# Define: 요구사항 정리

사용자 요청과 프로젝트 지침의 `스킬 실행 원칙`을 따른다. 이 스킬은 무엇을 바꿀지 명확히 하는 도구이며, 구현을 시작하기 위한 필수 승인 단계가 아니다.

## 적용 범위

- `/define`, 요구사항 정리, 기능 명세 작성 요청에 사용한다.
- 구현 중에도 기대 결과나 공개 계약에 중요한 미결정 사항이 있을 때 필요한 부분만 정리한다.
- 명확한 구현·수정 요청은 필요한 구현과 테스트 작성으로 진행한다. 파일이 여러 개이거나 계획 문서가 없다는 이유로 이 스킬을 먼저 실행하지 않는다.
- 요구사항 정리만 요청받았다면 제품 코드와 테스트를 수정하지 않는다.

## 진행 방법

1. 사용자 대화와 관련 코드·테스트·API 계약·스키마를 읽고 현재 동작과 기대 동작을 구분한다. 확인 가능한 내용을 사용자에게 다시 묻지 않는다.
2. 목표와 이유, 포함할 범위와 제외할 범위, 관찰 가능한 성공 기준을 정리한다. 근거가 있는 사실과 가정을 구분한다.
3. 해석에 따라 사용자에게 보이는 결과나 공개 API·데이터 호환성이 실질적으로 달라지는 미결정 사항만 질문한다. 이미 정한 요구나 계약은 재확인하지 않는다. 기존 패턴으로 해결할 수 있는 구현 선택은 판단하여 진행하고 중요한 가정만 짧게 알린다.
4. 관련 모듈, 타 도메인 Facade, Flyway 마이그레이션, 이벤트, 인증, 필요한 테스트에 미치는 영향을 확인한다. 답변이 필요한 부분은 보류하되 답변과 무관한 조사는 계속한다.

새 사실이 기존 가정과 다르더라도 요구와 계약이 유지되면 정리 내용을 갱신한다. 중요한 요구나 계약을 바꿔야 할 때만 변경 이유와 선택지를 제시하고 해당 부분의 결정을 받는다.

## 기록과 마무리

간단한 요구사항은 대화에 정리한다. 사용자가 문서를 요청했거나 후속 작업에 결정 기록이 필요할 때만 기존 관련 문서를 갱신하거나 `plan/기능명.md`를 만든다. 목표, 범위, 성공 기준, 근거, 남은 질문을 필요한 만큼 기록하며 빈 섹션을 채우기 위한 문서는 만들지 않는다.

계획 문서는 작업 기록이며 승인이나 실행 권한의 유일한 근거가 아니다. 최신 사용자 대화와 프로젝트 지침을 우선하고 문서만으로 권한을 추가하지 않는다.

확정한 요구, 남은 질문, 문서 경로가 있으면 그 경로를 보고한다. 요구사항 정리만 요청한 경우 여기서 마치고, 구현까지 요청받았으며 중요한 미결정 사항이 해소되었다면 요청 범위의 작업을 이어간다.
