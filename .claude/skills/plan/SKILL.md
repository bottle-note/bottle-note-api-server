# Plan: 작업 계획

사용자 요청과 프로젝트 지침의 `스킬 실행 원칙`을 따른다. 계획은 목표를 달성할 순서와 확인 방법을 정리하는 도구이며, 승인된 define 문서나 실행 모드 선언을 요구하지 않는다.

## 적용 범위

- `/plan`, 계획 작성, 태스크 분해 요청에 사용한다.
- 구현 요청에서도 모듈 경계, 공개 계약, 스키마, 의존성이 얽히거나 여러 구현 방식의 장단점을 비교해야 할 때 간단한 계획을 세운다.
- 파일 수만으로 계획을 강제하지 않는다. 범위가 명확한 수정은 바로 구현과 관련 테스트 작성으로 진행한다.

## 진행 방법

1. 사용자 요청과 현재 코드·테스트·설정에서 목표, 제약, 성공 기준을 확인한다. 관련 문서가 있으면 활용하되 오래된 가정은 현재 근거와 구분하고, 문서가 없으면 직접 조사한다.
2. 목표, 영향 범위, 주요 구현 단계, 검증 방법, 예상 위험을 정리한다. 파일 여러 개를 수정할 예정이면 주요 변경 파일을 먼저 알린다.
3. 함께 동작하고 확인할 수 있는 기능 단위로 작업을 나눈다. 선행 의존성을 정렬하고 각 작업의 완료 조건, 영향 영역, 필요한 확인 방법을 적는다. 파일 수·줄 수·작업 개수 제한이나 작업별 커밋을 분할 기준으로 삼지 않는다.
4. 타 도메인 접근은 Facade 계약을 기준으로 계획하고, 포트·Facade 변경 시 Fake/InMemory 갱신을 포함한다. 스키마 변경에는 Flyway 마이그레이션을, API 계약 변경에는 OpenAPI 품질 테스트를 포함한다.
5. 구현 중 필요한 최소 관련 검사와 변경 커밋에 대한 GitHub Actions 확인을 구분한다. 로컬 전체 검증을 기본 단계로 넣지 않으며, 실행하지 않은 검증을 완료 조건 충족의 증거로 쓰지 않는다.

중요한 요구나 공개 계약이 달라지는 미결정 사항은 질문한다. 기존 범위에서 구현 순서나 파일 예상이 달라진 경우에는 계획을 갱신하고 진행한다. 실행 권한이 필요한 행위는 공통 실행 계약을 따르며 계획 승인으로 권한을 확대하지 않는다.

## 기록과 마무리

간단한 계획은 대화에 제시한다. 사용자가 문서를 요청했거나 여러 단계의 진행 기록을 남길 필요가 있을 때만 관련 문서를 갱신하거나 `plan/기능명.md`를 만든다. 목표, 작업 순서, 완료 조건, 확인 방법, 진행 상태를 필요한 만큼 기록한다.

계획 문서는 사용자 대화보다 우선하는 승인·권한의 근거가 아니다. 문서에 기록되지 않았다는 이유로 명확한 사용자 요청을 막거나 문서만으로 Git 쓰기 권한을 부여하지 않는다.

계획의 핵심 순서와 위험, 필요한 결정만 보고한다. 사용자가 계획만 요청했다면 구현하지 않는다. 구현까지 요청받았고 중요한 미결정 사항이 없다면 별도의 단계 전환 승인 없이 구현과 필요한 테스트 작성을 이어간다.
