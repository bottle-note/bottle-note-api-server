# Plan: 알림 운영 정책과 발생처 확장 1차

Status: In Progress

## Overview

관련 이슈는 `bottle-note/workspace#383`이며, 발생처 확장에 필요한 `bottle-note/workspace#373`의 활동 이벤트 공동화를 포함한다. 기존 댓글·문의 답변 알림을 보존하면서 대댓글·좋아요·팔로우·베스트 리뷰 선정 알림과 유형별 수신 설정을 추가한다.

2026.09.05 사용자는 앞서 제안한 1차 구현을 진행하고 구현·검증을 철저히 수행하되 verify는 GitHub Actions에서 실행하도록 요청했다. 아래 정책은 후속 사용자 승인으로 확정되었다.

### Assumptions

1. 이번 발생처 범위는 기존 리뷰 댓글·문의 답변과 신규 대댓글·리뷰 좋아요·새 팔로워·베스트 리뷰 선정이다. 팔로우한 사람의 새 리뷰, 쪽지, 공지, 신고 결과, 사업자 문의 답변과 계정 제재 알림은 후속으로 남긴다.
2. 대댓글은 기존처럼 리뷰 작성자에게 알리면서 직접 답글을 받은 부모 댓글 작성자에게도 알린다. 행위자 본인은 제외하고 두 수신자가 같으면 하나만 생성한다. 수신 설정 때문에 한 경로가 제외돼도 다른 유효한 경로의 알림은 유지한다.
3. 좋아요·팔로우는 활성 상태로 바뀔 때만 알림 대상이며 취소와 동일 상태 반복 요청에는 생성하지 않는다. 취소 후 재활성화하더라도 동일 좋아요·팔로우 관계의 수신자 알림은 최초 한 건만 유지하는 안을 제안한다. 수신 거부 중 건너뛴 과거 활동을 설정 활성화만으로 소급 생성하지 않는다.
4. 베스트 리뷰는 기존 선정 상태와 이번 성공한 선정 결과를 비교해 새로 진입한 리뷰 작성자에게 알린다. 선정 유지와 동일 배치 재실행은 중복 생성하지 않는다. 탈락 후 다시 선정되면 새로운 선정 사건으로 한 번 알린다. 첫 배포 때 이미 선정되어 있는 리뷰에는 과거 선정 알림을 만들지 않는다.
5. 댓글·대댓글·좋아요·팔로우·베스트 리뷰·문의 답변의 여섯 유형을 사용자별로 설정하며 기본값은 수신 허용으로 제안한다. 설정을 끄면 해당 유형의 향후 인앱 알림 생성을 생략하고 기존 알림과 History는 유지한다. 잔존 `user_push_configs`의 전달 채널 설정을 인앱 설정으로 임의 전용하지 않는다.
6. 읽음 여부는 기존 `is_read`, 최초 읽음 시각은 `read_at`, 전달 상태는 `status`로 유지한다. 목록의 기존 envelope·필터·cursor·미읽음 집계·totalCount 계약을 유지한다. 기존 Action 버전의 payload 의미를 바꾸지 않고 댓글 없는 리뷰와 팔로우 대상 식별 계약을 추가한다.
7. 원본 활동이 rollback되면 알림과 History를 생성하지 않으며, 활동 이벤트의 관측은 한 번이고 History와 Notification이 각자 처리한다. 한 수신자나 중복 알림 처리 실패가 다른 수신자의 정상 알림을 취소하지 않아야 한다. 다중 인스턴스의 중복 방지는 공유 저장소에서 보장한다.
8. 이번 문서는 #383의 1차 범위다. 보관 기간·삭제 또는 아카이브 실행 주체와 실제 예상 데이터 규모에 따른 성능 목표는 별도 확정 대상이며, 이 항목이 남은 동안 #383 전체를 완료했다고 표시하지 않는다. 이 단계에서 운영 데이터 삭제·아카이브를 실행하지 않는다.

### Success Criteria

1. 기존 리뷰 댓글과 문의 답변의 수신자·본문·Action·읽음 계약이 유지되고 문의 재답변은 기존처럼 문의별 알림 한 건만 유지한다.
2. 대댓글의 리뷰 작성자·부모 댓글 작성자·행위자 조합과 중복 수신자 조합에서 예상 수신자별 알림 건수가 일치한다.
3. 좋아요·팔로우의 최초 활성화, 같은 요청 반복, 취소, 재활성화, 자기 자신에 대한 행위를 구분해 승인한 정책대로 알림을 생성한다.
4. 베스트 리뷰 신규 선정·유지·탈락·재선정·배치 재실행·중간 실패를 검증하고 선정 기준 자체는 변경하지 않는다.
5. 인증 사용자는 자신의 유형별 수신 설정만 조회·변경할 수 있으며 기본값, 부분 변경, 동시 변경, 잘못된 유형과 타 사용자 접근을 검증한다.
6. 대상 유형의 수신 거부는 기존·신규 발생처에 일관되게 적용되고 다른 유형, 기존 알림과 History에 영향을 주지 않는다.
7. 댓글과 좋아요의 원본 활동은 단일 이벤트로 관측하며 기존 History 내용과 기록 조건이 회귀하지 않는다. 이벤트 payload 및 cross-domain 접근은 프로젝트 레이어 표준을 따른다.
8. 같은 이벤트의 순차·동시 재전달과 다중 수신자 중복이 DB에서 수신자별 한 건으로 수렴하며, rollback 때 생성되지 않고 알림 저장 실패가 원본 활동을 되돌리지 않음을 통합 테스트로 확인한다.
9. 신규 Action과 필터값의 JSON/OpenAPI 계약을 검증하고 기존 Action, 미지원 버전 fallback, 목록·cursor·미읽음·최초 읽음·사용자 격리의 회귀 테스트를 통과한다.
10. 필요한 Flyway 변경은 기존 데이터를 보존하고 Product/Admin의 기동 validate 및 Batch 마이그레이션 제외 가드를 통과한다.
11. GitHub Actions에서 단위·아키텍처·Product/Admin 통합·OpenAPI·변경된 Batch 동작 테스트와 빌드를 실행한다. 최종 backend HEAD SHA와 CI 실행 SHA가 일치하며 모든 필수 job 성공과 실제 테스트 결과를 확인한다.

### Impact Scope

- `bottlenote-mono`: review, like, user, history, notification 도메인의 활동 이벤트, 수신자 정책, 인앱 수신 설정, Action과 영속성 계약.
- `bottlenote-product-api`: 인증 사용자 수신 설정 API 및 알림 OpenAPI·통합 테스트.
- `bottlenote-admin-api`: 기존 문의 답변 알림의 설정·회귀 통합 테스트.
- `bottlenote-batch`: 베스트 리뷰 선정 변화와 알림 연동, 재실행·실패 검증.
- `bottlenote-test-support`: Fake/InMemory 포트와 도메인 fixture.
- `git.environment-variables`: 수신 설정 및 선정 사건 영속화에 필요한 신규 Flyway의 필요성을 /plan에서 확정한다. 기존 마이그레이션은 수정하지 않는다.
- `.github/workflows/ci_pipeline.yml`: 변경된 Batch 테스트가 실제 검증에 포함되도록 범위를 보완한다.
- 앱·웹 UI와 라우팅 구현, FCM/APNs/SSE, 배포와 운영 데이터 변경은 포함하지 않는다.

## Execution Mode

- mode: delegated
- scope: plan, implement, test, self-review, verify, commit, push, pr
- GitHub 검증을 위해 backend 작업 브랜치와 필요한 schema 작업 브랜치를 commit·push한 뒤 기존 `ci_pipeline.yml`을 작업 브랜치에서 `workflow_dispatch`로 실행한다. 최종 작업 브랜치로 main 대상 PR을 생성하고 Actions 검증 증거를 기록한다.
- verify: GitHub Actions에서 수행한다. 로컬 Docker·Testcontainers·통합 테스트·전체 verify는 실행하지 않는다. 로컬 확인은 코드·diff·계약 정적 검토로 제한하고 실행 검증 통과를 주장하지 않는다.
- completion-evidence: 최종 HEAD SHA, Actions run URL, 필수 job 결과, 테스트 건수·실패 수, 남은 미검증 항목.
- stop-conditions:
  1. 승인된 가정이 깨지거나 성공 기준·범위가 바뀌는 발견.
  2. GitHub Actions 검증 실패를 세 번의 수정 시도 안에 해결하지 못함.
  3. merge·release·배포·운영 데이터 변경 등 위임 scope 밖의 행동이 필요함.
