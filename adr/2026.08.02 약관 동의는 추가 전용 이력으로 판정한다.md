# ADR: 약관 동의는 append-only 이력이며 유형별 최신 이력의 action으로 판정한다

- Decision Date(결정일): 2026.08.02 (Phase 1 2026.08.01, `EXPIRED`·마케팅 선택 동의 2026.08.02)
- Scope(대상): `bottlenote-product-api`, `bottlenote-mono` user 도메인, `git.environment-variables`
- Original Plan(원본 계획): `plan/complete/user-agreement-phase1.md`, `marketing-agreement.md`, `plan/agreement-expired-action.md` (git 히스토리)

## Context(배경)

동의 여부를 boolean 컬럼으로 두면 언제 어떤 원문에 동의했는지 감사할 수 없다. 이력 기반이면 재동의·철회·만료가 모두 이벤트로 남는다.

## Decision(결정)

- 동의 이력은 UPDATE/DELETE 없이 `AGREE`/`REVOKE` 이벤트를 계속 추가한다. 유형별 현재 상태는 `recorded_at`이 아니라 DB가 부여한 가장 큰 `id`의 action이다.
- 필수 유형은 `TERMS_OF_SERVICE`, `PRIVACY_COLLECTION_USE`이고 최신 이력이 `AGREE`일 때만 충족이다. 이력 없음·`REVOKE`·`EXPIRED`는 미충족이다. 두 필수 유형이 모두 충족돼야 `eligible=true`다.
- `MARKETING`은 `required=false`인 선택 유형이다. 전체 `eligible`과 로그인 힌트 `agreementRequired`는 필수 유형만으로 계산한다.
- `EXPIRED`는 서버가 기록하는 상태다. 클라이언트 제출 API는 `EXPIRED`를 `UNSUPPORTED_AGREEMENT_ACTION`(400)으로 거부한다. `EXPIRED`를 만드는 배치·운영 절차는 범위 밖이다.
- API는 `GET /api/v2/agreements/status`, `POST /api/v2/agreements`이며 인증 필수다. 제출 본문의 `content`는 클라이언트가 실제 표시한 원문이고 `inputContext`는 `INDIVIDUAL`/`BULK`만 허용한다. `user_id`, `recorded_at`은 서버가 채운다.
- 로그인 응답의 `agreementRequired`는 Evaluator 결과의 힌트일 뿐 접근 제어 근거가 아니다. AgreementGate와 보호 API의 403 자동 응답은 이번 범위에서 제외했다.
- 동의 유형과 action은 문자열 컬럼이라 유형·상태 추가에 스키마 변경이 필요 없다.

### Rejected Alternatives(선택하지 않은 대안)

- `recorded_at` 기준 최신 판정: 시각 동률과 클라이언트 시각 오염 문제가 있어 단조 증가 `id`를 쓴다.
- 유형별 YAML 정책과 기간 계산: 두 필수 유형 모두 필수라 정책 파일이 불필요했다.

## Status(상태)

Accepted(승인됨)

- Implementation Record(적용 기록): 적용됨

## Consequences(결과와 영향)

- 상태 응답은 `agreed` boolean 계약을 유지하고 최신 action 필드를 노출하지 않는다.
- 마케팅 메시지 실제 발송과 채널별 수신 설정은 별도 범위다.
