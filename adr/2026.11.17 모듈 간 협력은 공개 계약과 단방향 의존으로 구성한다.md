# 모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다

- Decision Date(결정일): 2026.11.17
- Scope(대상): 업무 모듈 사이의 직접 호출, 이벤트, 여러 업무의 데이터를 한 응답으로 묶는 조회

## Context(배경)

주류 상세는 리뷰를 담지만 리뷰 쓰기는 주류를 확인한다. 두 업무를 그대로 나누면 모듈이 서로를 의존한다. Facade interface만 추가해서는 타입을 소유한 모듈의 순환이 없어지지 않는다.

## Decision(결정)

운영 코드의 허용 방향은 다음과 같다. 화살표는 왼쪽이 오른쪽 타입을 사용한다는 뜻이며 업무의 중요도와 무관하다. 모든 업무 라이브러리는 foundation을 `api`로 공개하고, 그 밖의 업무 간 의존은 `implementation`으로 선언한다.

- foundation → observability
- user, alcohol, analytics → foundation
- storage → foundation, user
- community → foundation, user, alcohol, storage, observability
- history → foundation, user, alcohol, community, observability
- support → foundation, user, community
- notification → foundation, user, community, support
- content → foundation, user, alcohol, community, analytics
- access-control → foundation, user

Product와 Admin은 필요한 업무 라이브러리를 직접 선언한다. 두 앱은 서로를 의존하지 않는다. Batch main은 foundation, alcohol, community, support를 직접 선언하고 test에서는 user도 직접 쓴다.

### Public Contract(공개 계약)

타 업무의 기능은 Facade 등 명시한 공개 계약으로 호출한다. 공개 계약에는 반환값과 예외뿐 아니라 잠금과 트랜잭션 참여 조건도 포함한다. 모든 클래스에 interface를 추가하지 않는다. Controller는 앱의 공개 command/query 서비스와 조회 서비스를 직접 호출할 수 있다. Product FollowQueryService처럼 서비스가 공개 Facade를 구현할 수도 있다. 업무 검증과 VO 생성·트랜잭션 경계는 서비스가 맡는다. storage의 ResourceVerifierService, ResourceCommandService, ImageUploadService는 현재 규칙 검사에서 허용한 좁은 서비스 계약이다.

주류 병합은 alcohol이 `AlcoholMergeHandler`를 정의하고 관련 업무가 구현한다. alcohol이 구현 모듈을 거꾸로 의존하지 않는다. 앱이 필요한 구현과 역할을 빠짐없이 조립해야 한다.

### Queries Across Modules(여러 업무를 묶는 조회)

한 업무에서 끝나는 조회는 업무 모듈에 둔다. 여러 업무를 묶는 화면 조회는 사용하는 앱에 둔다. Product의 `AlcoholQueryService`와 사용자 복합 조회, Admin의 사용자·주류 조회가 그 예다. 각 앱이 조회 포트와 구현을 소유한다. 주류 상세는 로그인 사용자의 조회 이력과 SSR을 제외한 조회수 동작도 유지한다.

정렬·커서 때문에 필요한 읽기 전용 조인은 명확한 조회 클래스에서 허용한다. 삭제 표시·공개 범위·권한 조건을 보존한다. 이 허용은 타 업무 저장소로 쓰라는 허용이 아니다. 앱 조합에는 `AlcoholViewHistoryService`처럼 명시적으로 쓰는 서비스도 있으므로 모든 호출을 Facade 하나로만 제한한다고 설명하지 않는다.

### Calls and Events(직접 호출과 이벤트)

같은 트랜잭션에서 결과가 필요한 검증과 잠금은 직접 호출한다. 좋아요는 리뷰 행을 호출자 트랜잭션에서 잠근 뒤 저장한다. 의존을 줄이려고 잠금을 이벤트로 바꾸지 않는다.

리뷰·찜·별점은 community 소유 RegistryEvent를 `ApplicationEventPublisher`로 발행한다. history의 `HistoryRegistryListener`가 원래 트랜잭션에서 동기로 받아 기존 `HistoryEventPublisher`를 호출해 이력 metadata를 만든다. `HistoryListener`가 AFTER_COMMIT·비동기·REQUIRES_NEW로 저장한다. 모든 리스너를 비동기로 바꾸지 않는다. 좋아요 활동 이벤트는 history와 notification이 받는다. 이력은 반복과 취소도 기록하며, 알림의 중복 억제와 구분한다.

community는 history나 notification을 의존하지 않는다. 수신자인 history와 notification이 이벤트를 소유한 community를 의존한다. 이벤트가 컴파일 의존 자체를 없애는 것은 아니다.

## Status(상태)

Accepted(승인됨)

- Implementation Record(적용 기록): 사용자가 위임한 구현 범위에서 2026.11.17에 적용했다. 현재 작업 트리는 미커밋 상태다.
- 검증 근거: 최종 빌드 검사자의 결과를 읽어 확인했다. 지정한 로컬 사례 2,346개 중 2,345개 통과, 기존 성능 측정 1개 건너뜀, 남은 실패·오류 0개다. 이 문서 작성자는 Gradle을 실행하지 않았다.
- 검증 입력은 서브모듈 `e1beb652`의 SQL 32개 snapshot이다. 생성 리소스는 기존 로컬 SQL 30개 상태로 복원했다. 로컬 SQL 30개로 같은 검사가 통과했다는 뜻은 아니다. 기존 dirty gitlink는 보존했다.
- 원격 CI, 배포, 전체 성능, 선택하지 않은 전체 테스트는 미검증이다.

## Consequences(결과와 영향)

화면 조합을 앱에 두어 업무 모듈의 역방향 의존을 없앴다. 읽기 전용 조인은 테이블 변경의 영향을 받으므로 함께 검토해야 한다. 이벤트 항목 변경도 수신자에 영향을 준다.

Product와 Admin의 `app/rule/module/ModuleBoundaryRules`는 실제 출력 위치로 모듈 소유를 구분하고 허용 방향, 앱 역참조, 좁은 서비스 계약, 타 저장소 쓰기 메서드 호출을 검사한다. 검사는 적힌 범위만 강제한다. 메서드 이름 검사만으로 임의 SQL의 모든 쓰기를 막거나 모든 공개 클래스의 접근을 제한하지는 못한다. Gradle 방향과 공개 계약 리뷰를 함께 적용한다.
