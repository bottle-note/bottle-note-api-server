# 사용자 시나리오는 무상태로 평가하고 답변은 브라우저에 보관한다

- Decision Date(결정일): 2026.10.24
- Scope(대상): Product 시나리오 조회·평가 API, 어드민 시나리오 정의, 캠페인 콘텐츠 연동, 브라우저 답변 보관
- Related PRs(관련 PR): [어드민 시나리오 정의 관리 API #810](https://github.com/bottle-note/bottle-note-api-server/pull/810), [시나리오와 후보 검색 흐름 정리 #811](https://github.com/bottle-note/bottle-note-api-server/pull/811)

## Context(배경)

어드민은 속성 그룹 안에 여러 시나리오와 버전을 저장하고, 질문·선택지·명시적 이동 규칙을 정의한다. 기존 미리보기는 전달받은 답변으로 유효 경로와 다음 질문, 적용 조건, 후보 및 집계를 계산한다. 이 기능은 관리자용이며 사용자 실행을 저장하는 Product API는 아직 없다.

바텐더 노트에서 어드민의 추천 시나리오를 샘플로 실행하며 질문 순서, 분기, 이전 답변 수정, 가격·도수 선택지, 중간 종료와 재개를 검토했다. 이때 필요한 것은 특정 진입점에 고정된 추천 기능이 아니라 시나리오 ID를 받아 N개의 시나리오를 같은 방식으로 평가하는 기능이다. 캠페인 콘텐츠도 같은 시나리오를 연결해 사용해야 한다.

사용자는 브라우저에 보관한 답변으로 다시 추천받는다. 어제 같은 답변으로 50병이 나왔더라도 관리자가 주류·속성 연결 등을 변경해 오늘 45병이 된다면 45병을 보여주는 것이 요구사항이다. 이전 결과 집합이나 순서를 그대로 보존할 필요는 없다. 상세에서 돌아왔을 때도 답변과 화면 위치를 기억하면 되며, 서버가 추천 실행을 저장할 이유는 없다.

캠페인에는 참여했다는 사실을 기록한다. 기존 캠페인 이벤트의 `RESULT`는 결과를 노출했다는 사실이지 추천된 주류 목록을 보관한다는 의미가 아니다. 답변 이력이나 결과 분석은 참여 집계와 다른 책임이며 이번 결정의 저장 범위에 포함하지 않는다.

## Decision(결정)

### Stateless Evaluation(무상태 평가)

Product 시나리오는 조회와 평가 두 API로 제공한다.

| API | 책임 |
|---|---|
| `GET /api/v1/scenarios/{scenarioId}` | 사용자에게 제공 가능한 시나리오의 게시 정의 정보, 버전, 첫 질문과 선택지를 반환한다. |
| `POST /api/v1/scenarios/{scenarioId}/evaluate` | 요청에 담긴 전체 답변과 조회 의도를 검증하고 질문·선택지·최신 추천 후보를 반환한다. 도메인 데이터를 변경하지 않는다. |

- 호출자는 시나리오 ID를 전달한다. 서버가 바텐더 진입점 하나나 특정 속성 그룹·슬롯을 시나리오 선택의 고정 기준으로 삼지 않는다. 그룹 소속과 활성 여부 등 제공 가능 조건은 서버가 확인한다.
- 초안은 Product에 노출하지 않는다. 어드민이 게시하고 활성화한 정의를 사용한다. 로컬 샘플의 질문 생략 같은 교정은 Product가 별도로 하드코딩하지 않고 게시 정의에 반영한다.
- 평가 요청은 시나리오 버전, 순서 있는 전체 답변, 선택적으로 과거 질문 ID, `QUESTION` 또는 `RESULT` 조회 모드와 목록 페이징 정보를 담는다. 별도 `runId`, 실행 생성·저장·종료·재개 API는 만들지 않는다.
- 조회 응답은 정의의 버전을 명시한다. 평가 요청의 버전이 현재 제공 버전과 다르면 답변을 새 정의로 조용히 해석하지 않는다. 정의 재조회와 답변 재검증이 필요한 상태를 명시한다. 버전은 답변 해석의 호환성을 확인하기 위한 값이며 후보 데이터를 고정하는 값이 아니다.
- 응답은 평가에 사용한 버전, 유효 답변과 표시 문구, 현재 질문, 선택지별 문구·후보 수·선택 가능 여부, 이전 답변을 조회할 정보, 진행 상태와 후보를 제공한다. 프런트가 그래프 전체나 속성 저장 구조를 알아야 하는 계약으로 만들지 않는다.
- 후보·속성값·연결·맛 태그 등 검색 데이터는 평가 시점의 현재 상태를 읽는다. 브라우저 복귀, 재개, 결과 추가 조회도 다시 평가하므로 후보 수와 목록·순서가 이전 응답과 달라질 수 있다. 이전 실행 시점의 후보 스냅샷이나 고정 ID 집합은 저장하지 않는다.
- 결과 목록은 기존 Product 페이지네이션 원칙을 따른다. 페이징이 필요해도 같은 평가 API에 요청 정보를 전달하며 별도 실행별 추천 API를 추가하지 않는다. 페이지 사이 관리 데이터 변경에 따른 목록 변화는 결과 고정 기능으로 숨기지 않는다.

### User Actions(사용자 행동)

| 행동 | 평가 방식 |
|---|---|
| 다음 질문 | 현재 답변을 추가한 전체 답변을 `QUESTION` 모드로 평가한다. |
| 이전 질문 보기 | 답변은 보관한 채 `viewQuestionId`로 과거 질문을 지정한다. 후보와 선택지 집계에는 그 질문 직전까지의 답변만 적용한다. 조회만으로 답변을 삭제하지 않는다. |
| 답변 수정 | 수정한 질문까지의 답변만 제출한다. 서버는 시작 질문부터 순서와 분기를 검증하고 이후 질문을 다시 계산한다. 브라우저는 이전의 후속 답변을 폐기한다. |
| 바로 추천받기 | 화면에서 적용된 답변만 `RESULT` 모드로 제출한다. 현재 미응답 질문과 뒤 질문의 답변을 임의로 생성하거나 `ANY`로 채우지 않는다. 과거 질문을 보고 있다면 그 질문 직전의 답변까지만 적용한다. |
| 질문 더 보기 | 보관한 답변을 `QUESTION` 모드로 다시 평가한다. 유효 경로의 다음 미응답 질문부터 이어간다. |
| 상세에서 복귀 | 보관한 시나리오 ID·버전·답변으로 다시 평가하고, 브라우저가 결과 또는 질문 화면과 가능한 스크롤 위치를 복원한다. 후보는 현재 데이터로 갱신한다. |
| 처음부터 다시 하기 | 브라우저의 진행 상태를 비우고 같은 시나리오의 첫 질문을 조회한다. 서버 실행 삭제는 필요하지 않다. |

이동 규칙, 입력 검증, 검색 조건 합성, 선택지 집계는 서버가 소유한다. `QUESTION` 모드에서 정의의 `END`에 도달하면 결과 화면에 필요한 응답을 반환한다. `RESULT` 요청에 따른 사용자 중간 종료와 정의의 `END`는 응답에서 구분하되, 이 구분을 서버의 실행 상태로 저장하지 않는다.

### Answer Identity(답변 식별과 숫자 구간)

- 프런트는 서버가 발급한 `optionId`를 선택한다. `ANY`도 명시적인 선택지로 취급한다. 가격·도수 구간 계산, 경계 포함 여부와 검색 조건을 프런트가 만들지 않는다.
- 가격·도수 선택지는 현재 후보 값의 분포를 바탕으로 계산하고 같은 경계와 빈 구간을 정리한다. 서로 인접한 구간은 경계가 겹치거나 소수 값이 빠지지 않아야 한다. 후보가 단일 값으로 모이면 의미 없는 여러 구간을 만들지 않는다.
- 동적 구간의 `optionId`는 서버에 사용자 실행을 저장하지 않아도 원래 조건을 재현하고 위변조를 검증할 수 있는 식별자로 발급한다. 시나리오·정의 버전·질문·선행 답변 문맥과 실제 비교 조건을 결합한다. 저장된 답변을 새 후보의 분위수 순번으로 다시 해석하지 않는다.
- 예를 들어 어제 선택한 구간이 `13,000원 초과~15,000원 이하`였다면 오늘도 그 조건을 적용하고 일치하는 주류만 현재 데이터에서 다시 구한다. 후보 수 갱신과 선택했던 조건의 의미 변경은 구분한다.
- 현재 Admin `ScenarioAnswer.NUMBER_RANGE`는 양끝 포함인 `min/max`만 지원하고 미지원 필드를 거절한다. Product의 동적 선택지·배타 경계는 별도 계약으로 정의하고 기존 Admin 요청을 그대로 공개하지 않는다. 가능한 경로 평가와 검색은 기존 구현을 재사용하되 사용자 계약의 차이는 명시적으로 처리한다.
- 존재하지 않는 선택지, 다른 시나리오의 답변, 중복 질문, 유효 경로 밖의 답변과 잘못된 순서는 거절한다. 저장된 정의·답변이 현재 제공 조건과 호환되지 않는 상황은 복구 가능한 상태로 알려 재조회·재선택하게 한다. 조용히 답변을 제거한 추천을 정상 결과처럼 보여주지 않는다.

### Browser Storage(브라우저 보관)

- 시나리오 ID·버전, 확정 답변, 보고 있던 질문 또는 결과 모드와 화면 복원 정보는 브라우저 Local Storage에 보관한다. 서버에는 사용자별 질문·답변 이력, 실행 상태, 추천 결과 테이블을 추가하지 않는다.
- 보관 키는 사용자 문맥과 진입 문맥을 구분한다. 캠페인에서 실행했다면 캠페인 코드와 시나리오 ID를 포함해 다른 캠페인·시나리오의 답변을 섞지 않는다. 로그인 계정이 바뀌었을 때 다른 사용자의 보관 상태를 복원하지 않는다.
- 서버는 Local Storage 내용을 신뢰하지 않고 모든 평가 요청을 검증한다. 보관 데이터가 없거나 손상됐거나 질문·선택지가 바뀌면 첫 조회 또는 재선택으로 복구한다. 구체적인 보관 기간과 삭제 UX는 프런트 계약에서 정한다.
- 브라우저 데이터 삭제·기기 변경에 따른 답변 유실을 서버 실행 저장으로 보완하지 않는다. 기기 간 동기화와 서버 답변 이력은 별도 요구로 다룬다.

### Campaign Participation(캠페인 참여 기록)

- 캠페인 콘텐츠는 연결할 시나리오 ID를 참조할 수 있고 여러 캠페인 또는 진입점이 같은 시나리오를 사용할 수 있다. 평가 API는 캠페인 콘텐츠 ID를 필수 인자로 받지 않는다.
- 참여 기록은 기존 `POST /api/v1/campaign-contents/{code}/events`와 `VIEW·START·FINISH·RESULT` 이벤트를 사용한다. 평가 호출 자체가 참여 이벤트를 자동 저장하지 않는다. 이전 질문 조회·재평가·페이징이 새 참여로 중복 기록되지 않도록 프런트가 실제 사용자 행동 시점에 별도로 이벤트를 보낸다.
- 시나리오에서 결과 보기로 넘어가는 사용자 중간 종료도 기존 `FINISH`의 의미와 연결하고, 로그인한 사용자에게 결과를 실제로 노출했을 때 `RESULT`를 보낸다. 질문 더 보기와 재평가는 그 자체로 새로운 참여 시작이 아니다.
- `RESULT`의 로그인 요구, 회원·방문자 식별, 통계 집계와 제외 기준은 기존 캠페인 ADR을 따른다. 이 결정으로 기존 캠페인의 인증 정책을 바꾸지 않는다.
- 참여 이벤트에는 기존 식별·시각·유형을 기록하며 답변, 추천 주류 ID 목록·순서·개수나 개별 결과 내용을 추가하지 않는다. `RESULT`는 결과 노출 사실을 뜻한다. 평가 요청 본문이나 응답을 별도 이력으로 쌓아 이 경계를 우회하지 않는다.

### Cache and Tokens(캐시와 식별자)

- 첫 구현은 Redis나 JVM 캐시에 시나리오, 활성 상태, 선택지와 후보를 저장하지 않는다. 매 요청의 읽기 전용 트랜잭션에서 현재 활성 게시본과 검색 데이터를 조회한다. 관리자가 변경한 데이터는 커밋 후 시작하는 요청에 반영하며 캐시 무효화 이벤트 누락에 의존하지 않는다.
- 캐시를 도입하려면 시나리오 활성화·비활성화, 속성·연결 수정, 주류 수정·삭제와 맛 태그 변경을 포함하는 무효화 계약을 별도로 검증한다. 성능 측정 없이 캐시부터 추가하지 않는다.
- `optionId`는 별도 용도로 구분한 HMAC SHA-256 서명을 사용하고 현재·이전 서명 키는 기존 커서 키 설정으로 관리한다. 선택지에 시간 만료를 넣지 않으며 활성 버전과 선행 답변의 정규화된 조건을 검증한다. 키를 폐기하면 그 키로 발급한 답변은 400으로 거절하고 다시 선택하게 한다. 커서와 선택지의 서명 용도는 구분한다.
- 숫자 선택지는 DB에서 구한 25·50·75 분위 경계를 질문의 `step`에 맞춰 내림한 뒤 최대 네 구간으로 나눈다. 첫 구간은 양끝 포함이고 이후 구간은 하한 초과·상한 이하다. 중복 경계와 후보가 없는 구간은 제거한다. 여러 값을 가진 주류는 여러 구간에 속할 수 있지만 한 구간의 후보 수에는 한 번만 집계한다.
- 선택지별 개수는 같은 검색 조건을 사용한 DB 조건 집계 한 번으로 계산한다. 분위 경계도 DB에서 조회하며 전체 후보나 속성값을 애플리케이션 메모리로 가져오지 않는다.
- 결과는 `alcoholId` 오름차순으로 조회한다. HMAC keyset 커서는 시나리오·버전·적용 답변·페이지 크기에 결합하며 1시간 후 만료한다. 커서 만료 시 같은 답변으로 첫 페이지부터 다시 조회한다.

### Rejected Alternatives(선택하지 않은 대안)

- 서버 실행 CRUD와 답변·종료·재개·결과별 API: 클라이언트가 전체 답변을 보관하고 같은 평가를 다시 요청하면 충분하다. 현재 요구에 없는 실행 저장과 상태 전이·동시성·정리 작업이 늘어난다.
- 추천 대상 ID와 순서의 스냅샷 보관: 관리자가 바꾼 최신 후보를 보여주려는 요구와 맞지 않는다.
- 바텐더 전용 진입점으로 시나리오 고정 선택: N개의 시나리오와 캠페인 재사용을 지원하지 못한다.
- 그래프와 숫자 필터를 프런트가 평가: 플랫폼마다 이동·검색·집계가 달라지고 관리자 정의와 사용자 결과가 어긋난다.
- 동적 선택지를 매번 현재 분포의 동일 순번으로 재해석: 같은 답변을 복원했는데 사용자가 선택한 가격·도수 조건 자체가 달라진다.
- 평가 요청마다 캠페인 참여를 자동 저장: 이전 질문 보기·재개·페이징 같은 조회가 참여 집계를 늘린다.

## Status(상태)

Accepted(승인됨)

사용자와 합의한 설계 결정이다. ADR 승인과 배포·운영 검증은 구분한다.

### Implementation Record(적용 기록)

Product의 조회·평가 API와 서명한 선택지, 현재 데이터 재조회, 결과 keyset 페이징을 구현한다. 경로·답변 검증과 후보 조건 합성은 관리자 미리보기와 공유하고 관리자 JSON 계약은 유지한다. 별도 실행 저장소, 캐시와 마이그레이션은 추가하지 않는다. 구체적인 요청·응답 계약은 실행 중 OpenAPI로 제공한다.

브라우저 Local Storage 연동과 캠페인 화면의 시나리오 연결은 프런트 작업 범위다. 이번 서버 API는 기존 참여 이벤트를 변경하거나 자동 저장하지 않는다. 로컬 UI 샘플은 서버 계약이나 운영 검증을 대체하지 않는다.

## Consequences(결과와 영향)

- 같은 조회·평가 API를 N개의 시나리오와 여러 캠페인에서 재사용한다. 서버 실행 저장·만료·복원·이력 관리가 필요 없고 참여 집계는 기존 캠페인 도메인에 남는다.
- 상세 복귀나 다음 날 재평가 시 입력 조건은 보존하지만 추천 대상과 수·순서는 현재 데이터에 따라 달라진다. 화면은 이전 후보 수나 고정 결과를 보장하지 않아야 한다.
- 전체 답변을 매 요청마다 검증하고 집계를 다시 계산한다. 서버에 실행 상태가 없다는 이유로 경로 검증을 생략하거나 브라우저가 보낸 필터를 그대로 적용해서는 안 된다.
- 동적 선택지는 원래 조건을 재현하고 검증할 식별자와 정의 호환성 처리가 필요하다. 분위수 경계, 배타 비교와 후보 정렬은 서버 계약으로 확정하고 테스트해야 한다.
- 원본 Admin 미리보기의 요청·응답을 그대로 Product에 공개할 수 없다. 관리자 감사 정보와 편집 구조를 제외하고 사용자 화면에 필요한 형태로 변환해야 한다.
- 브라우저 저장소를 지우거나 기기를 바꾸면 진행 상태를 복원하지 못한다. 서버 저장 이력, 기기 간 재개, 과거 추천 재현과 개인별 답변 분석은 별도의 결정 없이는 제공하지 않는다.
- 캠페인 참여 이벤트는 참여 사실을 보여주며 사용자가 어떤 답변이나 추천 결과를 받았는지 설명하지 않는다. 그 분석이 필요해지면 기존 참여 이벤트에 결과를 덧붙이지 않고 목적과 저장 범위를 별도로 결정한다.
