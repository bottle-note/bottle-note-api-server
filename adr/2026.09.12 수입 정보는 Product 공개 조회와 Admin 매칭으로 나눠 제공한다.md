# 수입 정보는 Product 공개 조회와 Admin 매칭으로 나눠 제공한다

- Decision Date(결정일): 2026.09.12, 2026.09.24 개정
- Scope(대상): `bottlenote-product-api` 수입 정보 조회와 알코올 상세, `bottlenote-admin-api` MFDS 매칭 실행·후보 조회·확정·같은 제품 일괄 확정, `bottlenote-mono` MFDS 도메인
- Related Issues(관련 이슈): `bottle-note/workspace#429`, `bottle-note/workspace#448`

## Context(배경)

수입 정보는 식약처 수입 원장의 신고와 수입사다. 앱은 이 정보를 공개 조회하고, 관리자는 신고를 BottleNote 주류·증류소·지역에 연결한다. 두 용도는 같은 원장을 쓰지만 노출 범위와 쓰기 여부가 다르다.

Product 알코올 상세 `GET /api/v1/alcohols/{alcoholId}`에는 검증 완료 신고를 `mfdsDeclarations`로 중첩했었다. 이 방식은 주류 상세에 다른 자원을 얹은 것이라 OpenAPI에 수입 정보 그룹이 생기지 않았고, 사이드바에서도 찾을 수 없었다. 주류 상세의 `alcoholId`와 수입 주류의 `mfds_declarations.id`도 서로 다른 식별자다.

Admin 매칭은 수집기가 쓰는 실행·후보·근거 테이블과 신고의 후보 1~3번 고정 컬럼을 함께 썼다. Admin API는 고정 컬럼만 갱신했기 때문에, 최신 후보와 과거 `matching_run_id`가 서로 맞지 않을 수 있었다. 후보를 10개로 늘리려고 순위별 컬럼을 추가하면 이 중복은 더 커진다. 반면 기존 후보 테이블의 순위와 유일 키는 이미 10개를 수용한다.

관리자는 한 신고에서 고른 연결을 같은 제품의 다른 신고에도 한 번에 확정해야 한다. 용량·수입사·통관일이 달라도 같은 제품일 수 있다. 하지만 숙성·배치·캐스크·연도·숫자 에디션·캐스크 스트렝스가 다르거나 한쪽에만 있으면 같은 제품으로 단정할 수 없다. 미리보기와 확정 사이에 신고나 주류가 바뀔 수 있고 애플리케이션 인스턴스가 여러 개이므로, 검증값을 JVM 메모리에 둘 수 없다. 새 테이블을 만들면 스키마도 바꿔야 한다. 제품 동일성 키는 정제기가 `mfds-product-identity-v2`로 계산해 `product_identity_key_sha256`에 저장한다. 이 키에는 한글·영문 검색 키, 도수, 숙성 연수, 도수 유형이 들어가고 용량·수입사·배치성 번호는 빠진다.

## Decision(결정)

### Product 공개 조회

알코올 상세 응답에는 수입 신고와 수입사를 넣지 않는다. Product 전용 공개 payload와 `MfdsFacade` 공개 조회도 두지 않는다. 대신 읽기 전용 API를 `수입 정보` 태그로 묶어 제공한다. 인증 정책은 `PUBLIC`이다.

- `GET /api/v1/mfds/alcohols`: 수입 주류 목록
- `GET /api/v1/mfds/alcohols/{id}`: 수입 주류 상세. `{id}`는 `mfds_declarations.id`이며 BottleNote 주류 ID가 아니다.
- `GET /api/v1/mfds/importers`, `GET /api/v1/mfds/importers/{importerId}`: 수입사 목록과 상세
- `GET /api/v1/mfds/countries`: 원장에 등장한 수출국의 ISO Alpha-2 코드와 한글·영문명

목록은 Product HMAC keyset cursor를 쓴다. 요청은 `cursor`와 `size`, 응답은 `hasNext`와 `nextCursor`이며 `totalCount`는 없다. 수입 주류는 처리일자 내림차순으로 정렬하고, 처리일자가 같으면 `id` 내림차순이다.

수입 주류 목록의 검색 조건은 아래와 같다.

- `alcoholNameKo`: 공백을 trim한 뒤 `alcohol_name_ko`와 정확히 일치하는 행이다. 한 술의 과거 수입은 이 값으로 묶으므로, 수입사가 다른 병행 수입도 함께 나온다. 주류 상세 화면에 수입 내역을 붙일 때는 상세의 한글명을 넣는다.
- `alcoholId`: `selected_alcohol_id`가 이 값인 행이다. 매칭된 행만 보고 싶을 때 쓴다.
- `importerId`
- `exportCountry`: `export_country_alpha2`와 비교하는 ISO 3166-1 Alpha-2 코드다. 산지를 뜻하는 `Region`과 바꿔 쓰지 않는다.
- `alcoholType`: 기존 `AlcoholType` 이넘이다. `WHISKY`는 원장 `alcohol_category_ko`의 위스키에 대응한다.
- `processedDateFrom`, `processedDateTo`: 양 끝을 포함한다. 처리일자가 없는 행은 구간 조건에서 제외한다.
- `keyword`: `SearchKeywordTokenizer`로 공백을 나눠 AND로 결합한다. 토큰은 trim, 소문자 변환, 중복 제거를 거치고 `%`와 `_`는 일반 문자로 다룬다. 한 토큰은 `rcno`, 기본·SKU 제품명, 주류명, 주류 분류, `manufacturerName`, `importerBaseName`, 연결된 수입사의 `businessName` 중 하나에 부분 일치하면 통과한다.

수입사 목록의 `keyword`도 같은 규칙으로 `businessName`, `licenseNo`, `officialBusinessCode`, `representativeName`에 적용한다.

공개 조회는 `normalizationStatus = NORMALIZED`인 행만 내린다. 매칭 여부와 정규화 여부는 서로 다른 축이므로, 정규화가 끝난 미매칭 신고도 `alcoholId` 조건이 없으면 목록에 나올 수 있다. 응답은 Admin 응답 중 공개 가능한 부분집합이다. 처리일자는 `processedDate`(`YYYY-MM-DD`, 없으면 `null`)이고, `alcoholId`는 매칭된 경우에만 채운다. `volumeRaw`, `abvRaw`, 검토 메모, 원문, 정규화 사유·상태, 매칭 결정·후보, 수입사의 `adminNote`·`adminStatus`·검토 이력은 내리지 않는다. 매칭 실행·후보·확정 API는 이 태그에 두지 않는다.

### Admin 매칭 후보

Admin API는 `mfds_declarations`의 후보 고정 컬럼을 매핑하거나 참조하지 않는다. 매칭 실행 POST는 신고를 잠금 조회한다. 그다음 새 `mfds_matching_runs`, `mfds_matching_candidates`, `mfds_matching_evidence`를 저장하고, 같은 트랜잭션에서 신고의 실행 ID·버전·시각을 갱신한다. 후보가 없어도 완료된 실행을 남기며, 재계산으로 확정값을 바꾸지 않는다.

후보 조회·신고 상세·CANDIDATE 판정은 신고의 최신 실행 ID에 해당하는 후보를 쓴다. 그 실행은 완료 상태이고 신고의 계산 버전과 일치해야 한다. 조건이 맞지 않으면 빈 후보를 반환하고 고정 컬럼으로 대체하지 않는다. GET은 데이터를 이관하거나 계산하지 않는다.

주류 후보는 점수 0.4 이상 상위 10개, 증류소·지역은 각각 상위 3개다. v2 점수는 소수점 4자리로 계산·정렬·저장·응답한다. 수집기의 기존 raw score는 원래 척도로 반환하고, 버전이 다른 점수를 합쳐 순위를 만들지 않는다. v2는 원문을 우선해 브랜드와 제품 속성을 비교한다. 브랜드·숙성·배치·캐스크·연도가 명확히 다르면 점수를 제한하고, 값이 없으면 UNKNOWN으로 구별한다. 원문과 필드가 충돌하거나 제품명이 부족한 후보에는 `reviewRequired`를 표시하지만, 이 값이 자동 확정을 승인한다는 뜻은 아니다.

요소별 점수와 검토 상태는 evidence의 `ADMIN_SCORE_DETAIL_V2` 항목 `input_value`에 JSON으로 보존한다. 속성별 비교 결과도 별도 evidence로 저장하고 판정은 `rule_code`에 기록한다. 이 값은 합산 기여도가 아니라 판정 근거이므로 `weight`와 `evidence_strength`는 0으로 둔다. 그래야 수집기의 척도와 섞이지 않는다.

### 같은 제품 일괄 확정

일괄 확정은 `POST /admin/api/v1/mfds/declarations/{declarationId}/matching/bulk-preview`와 `bulk-confirm`이 담당하고, 단건 확정 경로는 그대로 둔다. 같은 제품 후보는 비어 있지 않은 동일성 키가 같은 신고다. 그 위에서 저장 숙성, 표시명의 숙성, 배치, 캐스크, 숫자 에디션, 연도, 캐스크 스트렝스, 도수 유형, 도수를 추가로 비교한다. 양쪽이 없거나 같으면 통과이고, 다르거나 한쪽에만 있으면 확인 필요다. 용량·수입사·통관일은 같은 제품을 가르지 않는다.

연결은 주류·증류소·지역을 각각 판정한다. 비어 있는 값만 채우면 적용 가능이고, 세 값이 이미 같으면 변경 불필요다. 변경 불필요인 신고는 판단 코드와 이력을 바꾸지 않는다. 기존 연결과 적용값이 다르거나 기존 값을 비우게 되면 충돌이다. 분류 우선순위는 충돌, 변경 불필요, 확인 필요, 적용 가능 순서다. 확인 필요에는 위 속성의 불일치와 한쪽 결측 외에도 버전·변이 표기 차이, 정제 검토 필요, 일반명 사유, 제조국 불일치, 관리자 해제 이력이 포함된다. 한 요청은 500건까지만 처리하며, 그룹을 잘라서 확정하지 않는다.

미리보기는 32바이트 난수 previewToken을 발급한다. 발급 기록에는 토큰, 관리자, 기준 신고, 적용할 3종, 만료 시각, 상태 해시를 담아 기존 Redis에 10분 TTL로 저장한다. 상태 해시는 만료 시각, 기준 신고, 적용할 3종, 주류 이름, 그룹 전체의 식별값과 현재 연결을 SHA-256으로 계산한 내부 값이다. 확정 요청은 토큰과 고른 신고 ID만 받고, 적용 대상은 발급 기록에서 읽는다.

확정은 토큰을 한 번 소비한 뒤 그룹을 신고 ID 오름차순으로 잠근다. 그리고 잠근 현재 행으로 상태 해시를 다시 계산해 발급 기록과 비교한다. 선택한 신고 중 하나라도 적용할 수 없으면 아무것도 쓰기 전에 거절한다. Redis 실패는 재시도하지 않는다. 요청이 거절되거나 롤백되어도 소비한 토큰은 되돌리지 않으므로, 관리자는 미리보기를 다시 받아야 한다.

적용한 신고의 선택 근거는 단건 확정과 같이 CANDIDATE, MANUAL, ALCOHOL_PROPAGATED로 남긴다. 감사 이력의 reason에는 `BULK_`와 기준 신고 ID를 붙이고, `selected_by`에는 관리자 ID를 남긴다. 일괄 해제와 새 자동 전파 기능은 만들지 않는다.

### Rejected Alternatives(선택하지 않은 대안)

- 주류 상세에 수입 신고를 중첩한다: 자원이 섞이고 수입 정보 그룹이 생기지 않는다. 태그 이름만 바꿔도 엔드포인트가 주류 상세라는 사실은 그대로다.
- 공개 경로를 `/mfds/declarations`로 둔다: 앱이 보는 단위는 신고가 아니라 수입 주류다.
- `GET /mfds/alcohols/{alcoholId}/history` 같은 이력 전용 API를 둔다: 목록의 `alcoholNameKo`·`alcoholId` 필터와 기능이 겹친다.
- 수출국을 `Region` 이넘이나 한글명 문자열로 받는다: 산지와 수출국은 다르고, 한글명은 표기가 갈라진다.
- 매칭 실행·후보·확정을 공개 수입 정보 태그에 둔다: 공개 조회와 관리 기능이 한 그룹처럼 보인다.
- 후보를 순위별 고정 컬럼으로 늘린다: 후보 테이블과 중복이 커지고, 후보 수를 바꿀 때마다 스키마를 바꿔야 한다.
- 미리보기 결과만 Redis에 두고 현재 행을 다시 보지 않는다: 그 사이에 생긴 변경을 놓친다.
- 동일성 키만으로 일괄 적용한다: 키가 같아도 배치나 캐스크가 다른 신고를 덮어쓴다.
- 일괄 확정의 결정값을 INHERITED로 쓴다: 기존 상속 갱신 경로의 대상이 된다.

## Consequences(결과와 영향)

- 앱은 주류 상세 응답만으로 수입 신고를 받을 수 없어, 수입 내역이 필요하면 `mfds/alcohols`를 한 번 더 호출해야 한다. 클라이언트는 `GET /api/v1/alcohols/{alcoholId}`와 `GET /api/v1/mfds/alcohols/{id}`의 식별자 의미를 구분해야 한다.
- 공개 조회에는 Admin DTO를 그대로 쓰지 않고 별도 응답 타입과 조회 경로를 둔다. `alcoholId` 검색은 `idx_declarations_selected_alcohol` 인덱스를 쓰며, 처리일자 정렬 목록이 커지면 `(processed_date, id)` 인덱스를 검토한다.
- 후보 개수를 바꿀 때 스키마를 바꿀 필요가 없고, 재계산 이력과 당시 점수 근거가 남는다. 삭제된 카탈로그 후보도 저장된 이름과 점수로 설명할 수 있다. 후보 저장이 실패하면 실행과 최신 연결도 함께 롤백된다.
- V22는 후보 1~3번 ID·점수 컬럼 18개를 기존 값 이관 없이 삭제하고 상세 조회 뷰를 다시 정의했다. 적용 전에 외부 수집기·정제기·대시보드가 고정 컬럼 참조를 제거한 버전으로 배포되어 있어야 한다. 수집기 전용 결과 화면이 Admin 실행까지 보여 주려면 별도 대응이 필요하다.
- 브랜드·제품명 추출은 규칙 기반이라 별칭과 한글·영문 표기 차이를 모두 해결하지 못한다. 점수는 정답 확률이 아니므로, 제품명이 부족한 신고는 사람이 확인해야 한다.
- 일괄 확정은 미리보기 당시의 그룹 전체와 기준 주류가 그대로일 때만 통과한다. 그룹이 커질수록 미리보기 응답과 잠금 범위도 커진다. 이름만 같고 식별 키가 다른 신고는 관련 내역 검색에만 나타난다.
- 일괄 확정한 신고는 단건 확정과 같은 결정값을 가지므로, 기존 Go 상속 배치가 이 신고를 씨앗으로 읽어 같은 키의 미선택 행에 연결을 퍼뜨릴 수 있다. 이미 확정된 행은 그 배치가 덮어쓰지 않는다. 이번 결정은 상속 배치의 동작을 추가하거나 끄지 않는다.
