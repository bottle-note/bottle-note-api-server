# ADR: 스키마 마이그레이션은 Liquibase CLI 대신 Flyway 기동형으로 한다

- 상태: 적용됨
- 결정일: 2026.07.25 (누락 시 빌드 실패 2026.08.15)
- 대상: `bottlenote-product-api`, `bottlenote-admin-api`, `bottlenote-batch`, `git.environment-variables`
- 관련 커밋: `cc030c73`, `b0c8ccd1`

## 결정

- 스키마는 Flyway가 애플리케이션 기동 시점에 적용한다. `ddl-auto`는 `validate`이며 Hibernate는 스키마를 만들거나 바꾸지 않는다.
- 마이그레이션 원본은 `git.environment-variables/storage/db/migration/V{n}__*.sql`에 두고, product-api와 admin-api의 `processResources`가 `classpath:db/migration`으로 복사한다. 저장소 소스 트리에는 `db/migration`이 없다.
- `baseline-on-migrate: false`다. 기존 스키마에 임의 baseline을 잡지 않는다.
- batch는 `flyway.enabled=false`이며 마이그레이션 주체가 아니다.
- 통합 테스트도 Flyway로 TestContainers 스키마를 만들고 별도 init 스크립트를 쓰지 않는다.
- 마이그레이션 리소스가 누락되면 빌드가 실패한다.

## 배경

2026.07 이전에는 `storage/mysql/changelog/schema.mysql.sql`의 Liquibase changeset을 개발·운영 DB에 CLI로 수동 적용했다(예: 큐레이션 v2 Phase 2, 증류소 컬럼 rename). 적용 여부가 사람 손에 달려 있어 엔티티와 스키마가 어긋난 채 배포될 수 있었고, 이미 적용된 changeset은 checksum 정책상 수정할 수 없어 CREATE 원문과 실제 스키마가 달라졌다. 기동형 전환 후에는 엔티티 변경과 마이그레이션이 같은 PR에 없으면 validate 단계에서 즉시 실패한다.

## 선택하지 않은 대안

이 전환은 계획 문서 없이 커밋으로 진행되어 Liquibase 기동형 등 대안을 비교한 기록이 남아 있지 않다. 위 배경은 이전 계획서(큐레이션 v2 Phase 2, 증류소 컬럼 rename)에 기록된 Liquibase CLI 운영 방식과 커밋 `cc030c73`, `b0c8ccd1`의 변경 내용에서 재구성한 것이다. batch를 마이그레이션 주체에서 제외한 근거도 명시 기록이 없으며 `CLAUDE.md`의 현행 설정만이 근거다.

## 결과와 비용

- 새 마이그레이션은 서브모듈 저장소에 추가하고 부모의 서브모듈 포인터를 갱신해야 반영된다. 두 단계 커밋이 필요하며 `commit -am`은 포인터를 조용히 실어 나르므로 명시적 `add`를 쓴다.
- 서브모듈 초기화 없이는 빌드와 통합 테스트가 실행되지 않는다.
- 버전 번호 충돌(예: V6 선점으로 Agent 마이그레이션을 V7로 교체)은 브랜치 병합 순서에 따라 발생할 수 있다.
