# ADR: 릴리즈 이미지 공개는 "게이트 → 빌드 → 서명 → 검증 → 승격" 단방향으로 원자화하고 핫픽스는 브랜치 네임스페이스와 워크플로 파일로 격리한다

- 상태: 적용됨 (api-server #743, 2026.09.04)
- 결정일: 2026.09.04
- 대상: `.github/actions/docker-build-push`, `deploy_release_applications.yml`, `deploy_development_applications.yml`, `deploy_batch.yml`, `release_pr_pilot_*.yml`. 같은 원자화 설계를 `admin-dashboard`, `bottle-note-frontend`에도 적용하며 `k8s-platform` 운영 가이드를 갱신한다. 핫픽스 격리(I7, 대안 C+D)는 핫픽스 자동화가 있는 `admin-dashboard`에만 적용된다. api-server와 frontend는 핫픽스 전용 자동화를 두지 않기로 했다(계획 개정 1).
- 관련 이슈·PR: `bottle-note/workspace#435`, `bottle-note/bottle-note-api-server#743`
- 사고 참조: admin-dashboard run `33374742687`(pull_request_target), `33374743149`(pull_request), 2026.08.31 08:49~08:51 UTC
- 원본 계획: `plan/2026.09.04 릴리즈 파이프라인 원자화 계획.md`, `2026.09.04 배포 상태 점검.md`, (git 히스토리). 도식: `adr/assets/2026.09.04 release pipeline flow.svg`(사고 재구성), `adr/assets/2026.09.04 release pipeline target.svg`(목표 구조)

## 결정

### 불변조건

| 번호 | 불변조건 |
|---|---|
| I1 | 릴리즈 run의 어느 job/step이 실패해도 `*_latest_production`이 가리키는 digest는 run 전후가 같다. |
| I2 | `*_latest_production`이 가리키는 digest는 항상 `cosign verify --key cosign.pub`를 통과한 digest다. |
| I3 | 승격은 재빌드 없이 태그 부착만 한다. 승격 후 채널 태그의 digest == 서명한 immutable 태그의 digest. |
| I4 | 릴리즈 run에서 buildx 캐시 export는 실행되지 않는다. dev run에서는 승격 이후에만, 실패해도 run을 실패시키지 않는다. |
| I5 | 이미지의 `GIT_COMMIT`은 게이트가 검증한 `source-sha`와 같다. |
| I6 | 릴리즈 PR 하나가 merge되면 배포 워크플로 run은 정확히 1개다. |
| I7 | (admin-dashboard) 핫픽스 릴리즈 브랜치는 자동화 경로만 만들며 `hotfixes/**` 네임스페이스를 쓴다. 핫픽스 검증은 표준과 다른 워크플로 파일이 소유한다. |
| I8 | 사고 시점의 미서명 운영 digest는 서명된 새 digest로 교체되고 그 코드는 main에 존재한다. |

### 공개 순서

composite action `docker-build-push`가 `immutable 태그 push → imagetools inspect → cosign sign(digest) → cosign verify → promote-tags를 digest에 태그 부착 → 승격 태그 digest 동등성·서명 재검증 → (dev만) 캐시 export`를 이 순서로만 실행한다. 승격 전 어느 단계가 실패해도 채널 태그는 바뀌지 않는다. immutable 태그는 Image Updater 대상이 아니므로(`allowTags: regexp:^<채널명>$` + `updateStrategy: digest`) 그것이 생기는 것은 운영 반영이 아니다. `both`의 Product/Admin은 독립 승격이므로 전체 run 실패 시 부분 반영 여부를 확인한다.

### 중복 gate 근절: 대안 C + D

- C: 표준 릴리즈 브랜치는 `releases/**`, 핫픽스는 `hotfixes/**`로 네임스페이스를 나눈다. 핫픽스 브랜치가 들고 오는 구 워크플로 스냅샷은 자기 `branches: ['releases/**']` 필터에서 탈락한다. 이것이 중복 실행을 막는 필요충분조건이다.
- D: admin-dashboard의 표준(`release_pr_merged.yml`)과 핫픽스(`hotfix_pr_merged.yml`) 워크플로 파일을 분리한다. api-server의 표준 게이트는 `release_pr_pilot_merged.yml`이며 핫픽스 파일은 없다. D는 중복 방지 수단이 아니라 "변경이 0이어야 통과"와 "변경이 있어야 통과"라는 정반대 불변조건을 한 게이트에서 떼어내고, 과거 어떤 스냅샷에도 없는 파일명으로 방어선을 이중화하기 위한 것이다.
- 세 레포 모두 트리거를 `pull_request_target`으로 통일한다. `pull_request_target`은 항상 default 브랜치의 워크플로 파일로 실행된다(GitHub 2025.11.07 변경).
- 고아 immutable 태그(sign/verify 실패로 서명 없이 남은 태그)는 1차에서는 유지하고 재시도 run이 같은 태그를 재사용한다. `promote-only` 모드는 필요가 확인되면 추가한다.

## 배경

2026.08.31 admin-dashboard 핫픽스 릴리즈에서 `pull_request`(릴리즈 브랜치의 구 워크플로 스냅샷)와 `pull_request_target`(main의 워크플로)이 같은 초에 동시에 실행됐다. 기존 action은 immutable 태그와 `*_latest_production`을 한 번의 push로 함께 올렸기 때문에, 검증 job이 실패한 run에서도 미서명 이미지가 운영 채널에 올라갔고 Image Updater(`--interval=30s`)가 18초 만에 write-back했다. 승격 후 사람이 되돌릴 시간이 없으므로 승격 앞의 게이트만이 유효한 통제 수단이다. 핫픽스는 정의상 과거 커밋에서 잘리므로 구조적으로 항상 낡은 워크플로 스냅샷을 들고 온다.

## 선택하지 않은 대안

- A: `pull_request_target` 통일 후 자연 수렴 + 생성 가드만 — 전환 후 첫 표준 릴리즈 전까지 핫픽스가 막힌다. 단독으로 부족하며 생성 가드는 정보성 요약으로만 남긴다.
- B: 핫픽스 릴리즈 브랜치에 워크플로 무력화 커밋을 얹음 — "릴리즈 브랜치 == 운영 소스" 논리가 깨지고, admin-dashboard `.dockerignore`가 `.github`을 제외하지 않아 이미지 컨텍스트와 digest도 달라진다.
- 승격 후 사후 롤백 자동화 — Image Updater 스캔 주기보다 느려 통제 수단이 되지 못한다.

## 결과와 비용

- 릴리즈 run에는 캐시 export가 없어 빌드 시간이 늘 수 있다. dev run은 승격 이후 best-effort로 export한다.
- 이미지 `GIT_COMMIT`/`GIT_BRANCH`는 `github.sha`가 아니라 게이트 출력 `source-sha`/`source-ref`에서 온다.
- 서비스별 핫픽스 지원 범위, 실패 대응, 검증된 `source_sha`·`release_key`·`deployment_mode` 전달 규칙은 `릴리즈 지침.md`가 현행 문서다.
- 사고 당시 운영에 떠 있던 admin-dashboard 핫픽스 코드(`fd6fd93`)는 main에 패치 동등 커밋이 없었다. I8에 따라 main 반영과 서명 digest 교체가 후속 절차다.
