# ADR: 방문자 식별은 서버 발행 `__Host-bn-visitor-id` 쿠키로 하고 인증·권한 판단에 쓰지 않는다

- 상태: 적용됨
- 결정일: 2026.07.16
- 대상: `bottlenote-product-api`, `bottlenote-observability`
- 관련 PR: `bottle-note/bottle-note-api-server#661`
- 원본 계획: `plan/complete/api-request-visitor-cookie.md` (git 히스토리)

## 결정

- Product API가 성공 응답에 `__Host-bn-visitor-id` 쿠키를 발행한다. 값은 서버 CSPRNG의 128-bit 이상 무작위 식별자이며, 클라이언트가 보낸 형식 오류 값은 신뢰하지 않고 교체한다.
- 속성은 `Max-Age=31536000`(발행 기준 고정 365일, sliding 갱신 없음), `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Domain` 미지정이다. `SameSite=None`은 웹뷰가 다른 site에서 직접 호출한다는 증거가 있을 때만 검토한다.
- 쿠키 값에 userId, IP, User-Agent 등 개인정보·권한 정보를 넣지 않으며, 이 값을 인증이나 권한 판단에 절대 사용하지 않는다. IP/User-Agent fingerprinting은 하지 않는다.
- 활동 로그 대상은 `/api/v1/**`, `/api/v2/**`의 2xx 응답, `GET/POST/PUT/PATCH/DELETE`만이다. `OPTIONS`, `HEAD`, Actuator, 정적 리소스, 3xx/4xx/5xx는 제외한다.
- DAU는 `visitor DAU`(KST 하루 고유 visitorId)와 `member DAU`(고유 JWT userId)로 분리 정의하고 합산하지 않는다.
- 로그에는 raw visitorId 대신 one-way digest를 남기고 JWT, Refresh Token, raw query, Cookie 헤더 전체는 기록하지 않는다.
- SSR 요청 부풀림을 막기 위해 브라우저가 다시 보내온 쿠키가 있는 요청만 DAU 후보로 기록하고, 최초 성공 응답은 쿠키만 발행한다.

## 배경

PR #661의 `ApiRequestConsoleLoggingFilter`가 요청 단위 로그를 남겼지만 브라우저·웹뷰 설치 단위를 이을 식별자가 없었다. 앱은 persistent WebView라 HTTP 쿠키 저장소를 쓴다. Next.js SSR이 `SERVER_URL`로 직접 호출하는 요청은 브라우저 쿠키를 전달하지 않아, 쿠키 없는 요청마다 새 방문자를 만들면 DAU가 부풀 위험이 있었다.

## 선택하지 않은 대안

- 2년 만료: Chrome persistent cookie 상한 400일보다 길고 데이터 최소화에 어긋난다.
- sliding expiration: 사실상 무기한 추적이 된다.
- IP·User-Agent·`Sec-Fetch-*`로 SSR 구분: 신뢰성이 부족하다.
- 프론트가 최초 page response에서 쿠키 발행: 정확도는 높지만 범위가 넓어져 후속으로 남겼다.

## 결과와 비용

- 최초 1회 방문 후 후속 API 요청이 없는 사용자는 DAU에서 누락될 수 있다.
- 쿠키 삭제, 앱 재설치, 다른 브라우저는 새 방문자로 센다. 쿠키는 사람이나 기기를 증명하지 않는다.
- 이후 `bottlenote-observability`의 `VisitorTelemetry`로 확장됐다. 개인정보 처리방침 반영과 실제 WebView 왕복 검증은 운영 후속 항목이다.
