# ADR: batch는 독립 상주 애플리케이션으로 운영하고 컴포넌트 스캔을 명시 범위로 제한한다

- Decision Date(결정일): 2026.01.22 (스캔 축소와 리소스 격리는 2026.06 보강)
- Scope(대상): `bottlenote-batch`, `bottlenote-product-api`, `git.environment-variables`
- Original Plan(원본 계획): `plan/complete/batch-module-separation.md`, `batch-component-scan-scope.md`, `batch-critical-hardening.md` (git 히스토리)

## Context(배경)

batch 모듈이 product-api 안에서 같이 기동되어 API 배포와 배치 실행이 묶여 있었고, `BestReviewReader` 무한 루프 같은 배치 결함이 API 프로세스에 영향을 줬다. 분리 후에도 `scanBasePackages = "app"` 전체 스캔이 남아 있어 배치가 필요 없는 product/admin bean까지 올렸고, 실행 JAR에 배포 매니페스트·kubeconfig·SOPS env가 함께 패키징되는 문제가 있었다.

## Decision(결정)

- `bottlenote-batch`를 product-api의 의존성에서 떼어내 별도 Spring Boot 실행 JAR(`BatchApplication`)로 만들고, Kubernetes에서는 CronJob이 아니라 상주 Deployment로 운영한다. Quartz 내장 스케줄러가 Job을 기동하기 때문이다.
- 헬스체크는 mono가 web 의존성을 가지므로 톰캣 actuator를 그대로 쓰고 포트만 8082로 분리한다.
- 설정은 profile include 없이 batch 전용 `application.yml`을 둔다.
- 컴포넌트 스캔은 `app` 전체가 아니라 `app.batch.bottlenote`로 제한하고, daily report에 필요한 mono bean(`DailyDataReportService`, `WebhookConfig`, `AppInfoConfig`)은 `@Import`로 명시한다. product/admin 성격의 bean이 batch context에 로드되지 않는 것을 `BatchApplicationContextTest`로 고정한다.
- batch 실행 산출물에는 `git.environment-variables` 전체가 아니라 `storage/mysql/sql`의 지정 쿼리 리소스만 포함하고, JWT secret·nonce salt의 하드코딩 기본값을 제거한다.
- DB 커넥션 풀은 프리티어 DB 상한을 고려해 product-api 10~15, admin-api 5, batch 3으로 배분한다.

### Rejected Alternatives(선택하지 않은 대안)

- CronJob 방식: Quartz 스케줄과 Spring Batch 영속 상태를 그대로 쓰기 위해 상주형을 택했다.
- JPA entity/repository 스캔까지 동시에 축소: context 안정성과 분리해 판단하기로 하고 컴포넌트 스캔만 먼저 줄였다.

## Status(상태)

Accepted(승인됨)

- Implementation Record(적용 기록): 적용됨

## Consequences(결과와 영향)

- batch 배포는 `deploy_batch.yml` 수동 dispatch로 API와 독립됐다.
- batch가 mono의 서비스 bean을 새로 쓰려면 `@Import`를 명시해야 한다. 암묵적 스캔에 의존할 수 없다.
- `verifyBatchPackagedResources`가 리소스 누락·금지 항목을 검사하지만 build·CI에 자동 연결되어 있지 않다(`CLAUDE.md`).
