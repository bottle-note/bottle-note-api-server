# 업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다

- Decision Date(결정일): 2026.11.17
- Scope(대상): `bottlenote-mono`에 있는 업무 코드와 공통 코드, 세 실행 앱이 build 파일에 적는 모듈 의존
- Related ADRs(관련 문서): [멀티모듈 분리는 하향식(top-down) 최소 웹 계층 분리로 한다](<2025.10.09 멀티모듈 분리는 하향식 최소 웹 계층 분리로 한다.md>), [모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다](<2026.11.17 모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다.md>), [업무 Fake와 fixture는 소유 모듈에 두고 테스트 인프라는 공유한다](<2026.11.17 업무 Fake와 fixture는 소유 모듈에 두고 테스트 인프라는 공유한다.md>)

## Context(배경)

이 문서에서 모듈은 Gradle이 따로 빌드하는 코드 묶음을 뜻한다. 모듈마다 build 파일이 하나 있고, 그 파일에 이 모듈이 사용할 다른 모듈을 적는다. 어떤 모듈을 컴파일할 때 쓸 수 있는 다른 모듈의 코드는 그 모듈의 컴파일 경로에 있는 것뿐이다. 컴파일 경로에는 build 파일에 직접 적은 모듈과, 그 모듈이 `api`로 전달한 모듈이 들어간다.

### Current Structure(현재 구성)

저장소에는 모듈이 6개 있다([settings.gradle](../settings.gradle)).

- 실행 앱 3개: `bottlenote-product-api`(일반 사용자 HTTP API, Java), `bottlenote-admin-api`(운영자 HTTP API, Kotlin), `bottlenote-batch`(배치 작업). 각 앱은 실행 jar를 따로 만들고 따로 배포한다.
- 라이브러리 3개: `bottlenote-mono`, `bottlenote-observability`(로깅·메트릭·추적), `bottlenote-test-support`(테스트 지원).

세 앱은 모두 mono 전체를 의존한다([product-api](../bottlenote-product-api/build.gradle), [admin-api](../bottlenote-admin-api/build.gradle.kts), [batch](../bottlenote-batch/build.gradle)). mono에는 업무 규칙, 저장소, 응답 타입, 보안 설정, 외부 연동 코드가 함께 들어 있다. `app.bottlenote` 아래에 업무 패키지가 17개 있고, 크기는 Java 파일 274개인 주류(`alcohols`)부터 8개인 `agent`까지 다양하다. 그 옆에 공통 패키지 `global`, `common`과 외부 연동 패키지 `app.external`이 있다.

이 구성은 [2025.10.09 결정](<2025.10.09 멀티모듈 분리는 하향식 최소 웹 계층 분리로 한다.md>)에서 나왔다. 그 결정은 웹 진입점만 실행 앱으로 떼어 내고 나머지 코드를 모두 mono에 두었다. 그래서 업무와 업무 사이의 규칙은 build 파일이 아니라 패키지 규칙과 ArchUnit 검사(`./gradlew check_rule_test`)로 지킨다.

### Problem(문제)

첫째, build 파일이 업무 사이의 의존을 보여 주지 않는다. 모든 업무가 같은 jar 안에 있으므로, 한 업무의 코드가 다른 업무의 어떤 클래스를 주입해도 컴파일된다. 주류 삭제가 그 예다. [AdminAlcoholCommandService](../bottlenote-mono/src/main/java/app/bottlenote/alcohols/service/AdminAlcoholCommandService.java)는 리뷰나 별점이 남아 있는 주류의 삭제를 거절하려고 리뷰와 별점의 저장소(`ReviewRepository`, `RatingRepository`)를 직접 주입한다. 프로젝트 지침([CLAUDE.md](../CLAUDE.md)의 레이어 표준 6)은 다른 업무의 저장소를 직접 쓰지 못하게 하지만, 이 코드는 그대로 빌드된다. 리뷰어는 import 목록을 읽어야만 이 의존을 알 수 있다.

둘째, 한 업무를 고칠 때 어디까지 읽어야 하는지 정하는 기준이 없다. 사람 리뷰어와 AI 코딩 도구는 모두 mono 전체를 영향 범위의 후보로 보아야 한다. 앱도 필요한 부분만 고르지 못한다. batch는 자기 패키지만 스캔하고 mono의 클래스 3개를 직접 등록하지만([BatchApplication](../bottlenote-batch/src/main/java/app/batch/bottlenote/BatchApplication.java)), 빌드할 때는 mono 전체를 의존한다.

셋째, 공통 패키지가 업무를 안다. 지침은 `global`이 어떤 업무도 모르게 하라고 정했다(레이어 표준 12). 그런데 `global` 안의 인증 코드는 사용자 업무의 타입을 import한다. [JwtTokenProvider](../bottlenote-mono/src/main/java/app/bottlenote/global/security/jwt/JwtTokenProvider.java)가 그 예다. 공통 코드가 업무 타입을 알면, 그 공통 코드를 쓰는 모든 곳이 그 업무의 코드까지 함께 의존하게 된다.

### Constraints(제약)

- 공개 HTTP API, DB 스키마와 저장된 값, 세 앱의 배포 절차는 바꾸지 않는다. Product와 Admin은 mono의 엔티티를 사용하고 같은 마이그레이션 SQL을 패키징한다. Batch에는 JDBC로 SQL을 직접 실행하는 작업이 있다. 세 앱이 운영에서 접속하는 DB는 이 문서를 쓰면서 확인하지 않았다.
- 2025.10.09 문서는 presentation, application, domain 같은 계층 단위로 모듈을 나누려다 순환 의존 때문에 그만두었다고 기록한다. 이 문서는 그 기록이 말하는 원인을 다시 검증하지 않았다. 이 문서의 근거는 그 기록이 아니라 위에서 직접 확인한 현재 코드다.
- 서비스와 Fake를 생성자로 조립하는 단위 테스트 방식은 계속 쓸 수 있어야 한다. 이 제약은 [테스트 준비 코드 문서](<2026.11.17 업무 Fake와 fixture는 소유 모듈에 두고 테스트 인프라는 공유한다.md>)가 다룬다.

## Decision(결정)

mono를 업무 책임에 따라 여러 Gradle 모듈로 나눈다. 세 실행 앱과 그 배포 단위는 그대로 둔다.

1. mono의 코드를 업무 책임 단위의 모듈로 옮긴다. 모든 코드를 옮긴 뒤에는 mono를 남기지 않는다.
2. 계층 단위로는 나누지 않는다. 업무마다 presentation, application, domain, infrastructure 모듈을 일률적으로 만들지 않는다.
3. 실행 앱은 Product, Admin, Batch 세 개를 유지한다. 공개 HTTP API의 요청·응답·오류, DB 스키마와 저장된 값, 배포 절차를 바꾸지 않는다.
4. 모듈을 나누어도 DB는 나누지 않는다. 모든 모듈은 지금 쓰는 DB를 그대로 함께 쓴다. 이 분리는 업무별 DB 분리나 업무별 독립 배포(MSA)가 아니고, 그 준비 단계도 아니다. 한 요청이 여러 업무의 테이블을 한 트랜잭션으로 바꾸는 현재 동작도 유지한다.
5. 모든 소스 파일과 리소스는 소유 모듈이 하나다. 소유를 정하지 못한 코드를 공통 모듈에 임시로 넣지 않는다.
6. 공통 기반 모듈에는 특정 업무의 타입, 테이블 구조, 규칙을 알아야 하는 코드를 두지 않는다. import 유무는 이를 확인하는 단서일 뿐이다. 업무 타입을 import하지 않아도 업무 테이블을 직접 읽는 SQL이나 업무 규칙을 담은 코드는 공통 기반에 둘 수 없다. 특정 업무를 아는 인증, 감사 기록, 외부 연동 코드는 그 업무 모듈이나 그 코드를 쓰는 앱이 가진다.
7. 모듈의 운영 코드 사이 의존은 되돌아오지 않게 한다. A가 B를 쓰면 B는 A를 쓰지 않는다. 여러 모듈을 거쳐 A로 돌아오는 경로도 두지 않는다. 서로를 필요로 하는 업무를 어떻게 한 방향으로 만드는지는 [모듈 간 협력 문서](<2026.11.17 모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다.md>)가 정한다.
8. 세 앱은 자기에게 필요한 모듈을 build 파일에 적어 조립한다. Batch에 빠진 bean(Spring이 등록해 관리하는 객체)이 생겼을 때 스캔 범위를 `app` 전체로 넓히는 것을 기본 해결책으로 삼지 않는다. Batch가 쓰지 않던 웹·보안 설정과 이벤트 리스너까지 함께 등록되기 때문이다.
9. 모든 클래스에 interface를 두는 것과, 모든 업무를 계약 모듈과 구현 모듈의 쌍으로 나누는 것은 의무가 아니다.

### Why Gradle Modules(Gradle 모듈을 고른 이유)

지금의 경계는 사람이 규칙을 기억하고, ArchUnit이 규칙에 적힌 형태만 검사하는 방식으로 유지된다. 모듈로 나누면 다음이 달라진다.

- 어떤 모듈의 컴파일 경로에 없는 모듈의 타입을 쓰면 컴파일이 실패한다. 규칙에 적지 않은 형태의 의존도 같은 방식으로 막힌다.
- 모듈 사이의 의존이 build 파일에 한 줄로 적힌다. 새 의존을 추가하는 변경은 리뷰에서 그 한 줄로 드러난다.
- 한 업무를 고칠 때 읽을 범위의 출발점이 "그 모듈과 그 모듈이 build 파일에 적은 모듈"로 정해진다. 사람과 AI 도구가 변경 범위를 더 쉽게 파악할 것이라는 기대가 이 결정의 주된 동기다. 이 기대는 아직 측정하지 않았다.

Gradle이 대신해 주지 않는 일도 있다. 이 일들은 결정 뒤에도 사람이 관리해야 한다.

- 의존으로 적은 모듈 안의 `public` 클래스는 모두 쓸 수 있다. Gradle은 저장소 구현 같은 내부 클래스를 숨겨 주지 않는다. "다른 모듈은 공개하기로 정한 타입만 쓴다"는 규칙은 계속 코드 규칙과 ArchUnit으로 지켜야 한다.
- A가 B를 `api`로 선언하면 A를 사용하는 C도 컴파일할 때 B의 타입을 쓸 수 있다. C의 build 파일에 B가 적혀 있지 않아도 그렇다. 그래서 어떤 모듈이 무엇을 쓸 수 있는지는 직접 적은 의존과 `api`로 전달된 의존을 함께 보아야 알 수 있다. 지금은 test-support가 mono를 `api`로 선언한다([build 파일](../bottlenote-test-support/build.gradle)).
- 컴파일이 되는 것과 앱이 필요한 bean을 모두 등록해 기동하는 것은 다른 문제다. Product와 Admin은 `app` 패키지 전체를 스캔한다([ProductApplication](../bottlenote-product-api/src/main/java/app/ProductApplication.java), [Application.kt](../bottlenote-admin-api/src/main/kotlin/app/Application.kt)). 어떤 모듈이 앱의 의존에서 빠지면 그 모듈의 이벤트 리스너는 등록되지 않는다. 리스너를 주입받는 코드가 없으므로 기동 오류도 나지 않는다.

### Candidate Modules(검토 중인 후보 구성)

아래 표는 위 원칙을 현재 패키지에 적용해 본 후보다. 이 문서가 승인되어도 표에 적힌 모듈의 이름, 개수, 묶음은 승인되지 않는다. 모듈 사이의 의존 방향도 이 표로 정하지 않는다.

| 구분 | 후보 | 옮겨 올 현재 코드 | 맡을 책임 |
|---|---|---|---|
| 실행 앱 | product-api, admin-api, batch | 지금과 같다 | 컨트롤러와 배치 작업, 앱 설정, 필요한 모듈의 조립 |
| 업무 | user | `user`, `agreement`, `agent` | 계정, 프로필, 팔로우, 약관 동의, Agent 인증 |
| 업무 | alcohol | `alcohols`, `mfds` | 주류 정보, 수입 신고 정보 |
| 업무 | community | `review`, `rating`, `picks`, `like` | 리뷰, 별점, 찜, 좋아요 |
| 업무 | history | `history` | 사용자 활동 이력 |
| 업무 | notification | `notification` | 알림 생성, 수신 설정 |
| 업무 | content | `banner`, `curation`, `campaigncontent` | 배너, 큐레이션, 캠페인 콘텐츠 |
| 업무 | support | `support` | 문의, 신고, 사용자 차단 |
| 업무 | analytics | `statistics` | 방문자 통계 |
| 업무 | access-control | `accesscontrol` | IP 차단 |
| 앱 지원 | web-support | `global`의 웹 요청 처리 코드 | 두 웹 앱이 함께 쓰는 HTTP 공통 처리 |
| 앱 지원 | query | 여러 업무의 데이터를 묶어 화면 응답을 만드는 코드 | 여러 앱이 함께 쓰는 화면 응답 조합 |
| 공통 기반 | foundation | `global`, `common` 중 업무를 모르는 코드 | 공통 타입 |
| 공통 기반 | observability | 지금과 같다 | 로깅, 메트릭, 추적 |
| 공통 기반 | test-support | 업무를 모르는 테스트 도구 | 테스트 인프라 |

아직 정하지 않은 것과, 그것을 정할 때 쓸 기준은 다음과 같다.

- community의 묶음: 쓰기 경로에서 서로의 타입이 필요하고 함께 바뀌는 업무만 한 모듈에 둔다. [ReviewService](../bottlenote-mono/src/main/java/app/bottlenote/review/service/ReviewService.java)는 별점 타입 `RatingPoint`를 쓰고, [LikesCommandService](../bottlenote-mono/src/main/java/app/bottlenote/like/service/LikesCommandService.java)는 좋아요를 저장하기 전에 리뷰 행을 잠근다. 따라서 review, rating, like를 함께 둘 근거는 코드에 있다. picks를 반드시 함께 두어야 하는 근거는 확인하지 못했다.
- query를 공유 모듈로 둘지: 한 업무 안에서 끝나는 조회는 그 업무 모듈에 둔다. 여러 업무의 데이터를 묶어 화면 응답을 만드는 코드는 그 응답을 쓰는 앱에 두는 것이 기본이다. 여러 앱이 같은 조합을 실제로 함께 쓸 때만 query 모듈을 검토한다. 상세 기준은 [모듈 간 협력 문서](<2026.11.17 모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다.md>)의 조회 항목을 따른다.
- foundation과 web-support의 범위: 결정 6을 통과한 코드만 foundation에 둔다. 지금의 `global`에는 사용자 업무의 타입을 쓰는 인증 코드가 있으므로 그대로는 들어갈 수 없다.
- 인증, 감사 기록, 차단한 사용자의 글을 가리는 코드([BlockWordSerializer](../bottlenote-mono/src/main/java/app/bottlenote/common/block/serializer/BlockWordSerializer.java)), `app.external`, Batch가 쓰는 일일 리포트의 소유: 그 코드가 알아야 하는 업무의 타입, 테이블 구조, 규칙을 가진 모듈이나, 그 모듈을 쓰는 앱이 소유한다. 결정 6을 통과한 부분만 공통 기반에 둘 수 있다. 일일 리포트([DailyDataReportService](../bottlenote-mono/src/main/java/app/bottlenote/support/report/service/DailyDataReportService.java))는 사용자, 리뷰, 좋아요 같은 여러 업무의 테이블을 SQL로 직접 센다. 이런 SQL은 import에 드러나지 않으므로, import만 보아서는 그 코드가 어느 업무를 아는지 가려낼 수 없다.

### Relation to the 2025.10.09 Decision(기존 결정과의 관계)

2025.10.09 문서는 세 가지를 정했다. 웹 진입점만 실행 앱으로 떼어 낸다. 나머지 코드는 모두 mono에 둔다. 계층 단위로는 나누지 않는다.

- 이 문서가 이어받는 것: 실행 앱이 웹 진입점을 갖고 업무 코드를 한 방향으로 쓴다는 구성, 그리고 계층 단위로 나누지 않는다는 선택.
- 이 문서가 바꾸는 것: 나머지 코드를 모두 mono에 둔다는 결정, 그리고 그 결과로 업무 사이의 경계를 모듈이 아니라 패키지 규칙과 ArchUnit으로만 지키던 운영 방식.

### Rejected Alternatives(선택하지 않은 대안)

- mono를 유지하고 패키지 규칙과 ArchUnit만 강화한다: 추가 비용이 가장 작고, 계속 유지할 수 있는 선택이다. 그러나 규칙에 적지 않은 형태의 의존은 막지 못하고, 세 앱이 mono 전체를 의존하는 구조도 그대로 남는다. 컴파일 단위의 분리가 필요하다고 판단해 고르지 않았다.
- 계층 단위 모듈로 나눈다: 2025.10.09 문서가 이미 선택하지 않은 방식이다. 이 문서는 그 방식으로 돌아가지 않는다.
- 모든 업무를 계약 모듈과 구현 모듈의 쌍으로 나눈다: 모듈 수가 두 배가 된다. 계약에 쓰는 타입이 다른 업무의 타입에 의존하지 않도록 정리하는 일도 모든 업무에 생긴다. 필요한 곳에서만 쓰는 방법으로 남긴다.
- 업무별로 DB를 나누거나 따로 배포한다: 배포 단위와 DB를 유지한다는 제약에 어긋난다.

## Status(상태)

Proposed(제안됨)

- 결정일 칸의 날짜는 이 제안을 작성한 날이다.
- Implementation Record(적용 기록): 미착수. 이 문서를 쓰면서 소스, build 파일, 지침 문서를 바꾸지 않았다.
- 검증 범위: 이 문서의 근거는 소스와 build 파일을 읽어 확인한 내용이다. 빌드, 테스트, 앱 기동은 실행하지 않았다. 후보 구성이 실제로 빌드되는지, 세 앱이 지금과 같은 bean으로 기동하는지는 확인되지 않았다.
- 승인 전까지는 [2025.10.09 문서](<2025.10.09 멀티모듈 분리는 하향식 최소 웹 계층 분리로 한다.md>)와 현재 지침이 기준이다. 이 문서가 승인되면 그 문서를 `Superseded(대체됨)`으로 표시하고 이 문서를 가리키게 한다.

## Consequences(결과와 영향)

### Positive(긍정적 영향)

- 업무 사이의 의존을 build 파일에서 확인할 수 있다. 주류 모듈의 컴파일 경로에 리뷰 모듈이 없으면, 주류 삭제가 리뷰 저장소를 쓰는 것과 같은 코드는 컴파일되지 않는다. 이때 다른 모듈의 `api` 선언으로 전달되는 의존도 함께 확인해야 한다.
- 한 업무의 변경을 검토할 때 읽을 범위의 출발점이 생긴다.
- Batch처럼 일부만 쓰는 앱이 필요한 모듈만 적을 수 있다. 실제로 얼마나 줄어드는지는 확인하지 않았다.

### Negative(비용과 부담)

- build 설정이 늘어난다. 루트 [build.gradle](../build.gradle)은 QueryDSL 생성 경로와 Spotless 대상을 모듈 이름으로 직접 나열하므로, 새 모듈에는 이 설정이 자동으로 적용되지 않는다. JPA 저장소를 찾는 설정([JpaConfig](../bottlenote-mono/src/main/java/app/bottlenote/global/config/jpa/JpaConfig.java))도 지금은 mono 안에 있어 새 위치를 정해야 한다.
- 소유를 정해야 하는 코드가 있다. `global`, `common`, `app.external`의 파일은 패키지 이름만으로 소유 모듈이 정해지지 않는다.
- 여러 모듈에 걸친 변경이 지금보다 번거로워진다. 다른 모듈이 쓰는 타입 하나를 바꾸면 그 타입을 쓰는 모듈을 모두 함께 고치고 다시 빌드해야 한다.
- 앱이 필요한 모듈을 빠뜨리지 않았는지 확인하는 검증이 새로 필요하다. 빠진 리스너는 오류를 내지 않기 때문이다.
- ArchUnit 검사 범위를 다시 확인해야 한다. 현재 규칙 검사는 product-api 테스트의 클래스 경로에서 `app.bottlenote`를 읽는다([AbstractRules](../bottlenote-product-api/src/test/java/app/rule/AbstractRules.java)). 새 모듈이 이 범위에 실제로 들어오는지는 확인하지 않았다.
- 테스트 준비 코드를 모듈마다 연결해야 한다. 이 비용은 [테스트 준비 코드 문서](<2026.11.17 업무 Fake와 fixture는 소유 모듈에 두고 테스트 인프라는 공유한다.md>)가 다룬다.
- 빌드 시간과 CI 시간이 줄어든다고 볼 근거는 없다. 측정하지 않았다.

### Neutral(중립적 영향)

- 이 문서가 승인되면 `CLAUDE.md`와 `AGENTS.md`의 모듈 구조 절, 그리고 레이어 표준 가운데 모듈 구성을 전제로 한 항목을 고쳐야 한다. 두 지침은 현재 6개 모듈 구성을 확정된 구성으로 적고 있다. 이번에는 지침을 고치지 않았다.
- 패키지 규칙과 ArchUnit은 없어지지 않는다. Gradle이 막지 못하는 규칙을 계속 맡는다.
