# ADR: 큐레이션 피드는 `feed_payload` Read Model로 읽고 스펙 지문 변경 시 재생성한다

- 상태: 적용됨
- 결정일: 2026.07.28 (쓰기 경로 2026.07.27, 복수 code 조회 2026.08)
- 대상: `bottlenote-mono` curation 도메인, `bottlenote-product-api`, `bottlenote-admin-api`, `git.environment-variables`
- 관련 이슈: `bottle-note/workspace#322` (원본 ADR)
- 원본 계획: `plan/complete/curation-feed-payload.md`, `curation-feed-read-path.md`, `multi-code-curation-feed.md` (git 히스토리)

## 결정

- `curation_extension.feed_payload`(JSON, nullable) 컬럼을 두고, 어드민이 큐레이션을 생성·수정할 때 원본 payload와 함께 `CurationFeedProjector.extractFeedPayload`(스펙의 `x-feed` 투영 + 숨은 입력값 병합)로 만든 feed_payload를 이중 쓰기한다.
- Product 피드와 Admin 프리뷰는 `CurationExtension.feedSource()`로 읽는다. feed_payload가 NULL이면 원본 payload로 fallback한다.
- 스펙 변경은 canonical JSON의 SHA-256 지문(`CurationSpecFingerprint`)으로 감지하고, 지문이 바뀐 스펙의 feed_payload를 무효화한 뒤 재생성한다(`CurationFeedPayloadRefreshService`: 공유 락, 무효화 선행, 실패 정책). NULL 레거시 행의 backfill도 같은 경로가 겸한다.
- 기존 데이터의 일괄 backfill은 하지 않는다. 어드민 재저장이나 스펙 변경 재생성으로 자연 반영한다.
- `GET /api/v2/curations/feed`는 `code`를 배열로 받아 OR로 조회하고, 후보 큐레이션 ID를 `size + 1`개까지만 먼저 뽑은 뒤 필요한 큐레이션·스펙·Extension을 일괄 조회한다. 존재하지 않는 코드만 오면 빈 결과다.

## 배경

피드 응답을 만들 때 전체 노출 큐레이션과 payload를 메모리에 올리고 Extension을 N+1로 조회했다. 스펙의 `x-feed` 규칙을 매 요청 해석하는 것도 비용이었다. workspace#322에서 읽기 모델을 분리하기로 결정했고, 이 저장소에서는 쓰기 경로 → 읽기 경로 → 조회 최적화 순으로 적용했다.

## 선택하지 않은 대안

- 스펙 버전 컬럼 추가로 변경 감지: 스키마 변경 없이 지문으로 해결했다.
- 재생성을 배치 Job으로 분리: 어드민 저장 경로와 동일한 서비스가 락을 잡고 처리하는 편이 순서를 보장했다.

## 결과와 비용

- 재생성 중 어드민 저장이 경합하면 파생값 세대가 어긋날 수 있다. `@Version` 도입은 스키마 변경 범위라 보류했다.
- 재생성 트랜잭션 chunk 처리는 수천 건 규모부터 필요하다.
- 피드 응답 payload는 API 계약이므로 `x-feed` 스펙 보정은 프론트와 협의 후 별도 PR로 한다.
