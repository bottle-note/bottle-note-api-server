# 업무 Fake와 fixture는 소유 모듈에 두고 테스트 인프라는 공유한다

- Decision Date(결정일): 2026.11.17
- Scope(대상): `bottlenote-test-support`와 각 모듈의 테스트 폴더에 있는 테스트 준비 코드, 그 코드를 쓰는 테스트의 의존 선언
- Related ADRs(관련 문서): [업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다](<2026.11.17 업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다.md>), [모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다](<2026.11.17 모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다.md>)

## Context(배경)

과거 test-support가 업무 모델과 Fake를 함께 모았다. 업무를 분리하면서 이 구조를 유지하면 테스트 준비 코드가 여러 업무를 다시 묶게 된다. 같은 이름의 Fake가 여러 경로에서 선택되던 문제도 정리해야 했다.

## Decision(결정)

업무 Factory·Fake·InMemory는 `module-domains/{모듈명}/src/testFixtures/java`에 둔다. 소비자는 필요한 모듈만 `testImplementation(testFixtures(project(":bottlenote-user")))`와 같은 방식으로 선택한다. Groovy build에서는 기존 Groovy 문법을 따른다. fixture를 다른 fixture의 공개 API로 일괄 재노출하지 않는다.

- user의 `FakeUserFacade`, 인증 테스트 지원은 user fixture가 소유한다.
- community의 `InMemoryReviewRepository`, 리뷰·별점·좋아요·찜 Factory는 community fixture가 소유한다.
- 여러 업무를 묶는 앱 전용 fixture와 조회 Fake는 해당 앱의 `src/test`에 둔다.
- test-support main의 Java 파일은 `TestContainersConfig`, `DataInitializer`, `FakeWebhookRestTemplate` 세 개다. 업무 Fake와 인증 헬퍼를 모으지 않는다.
- storage의 통합 테스트 fixture는 중립 test-support로 컨테이너 설정을 조립한다. 반대 방향으로 업무 fixture를 test-support에 모으지 않는다.

Service 단위 테스트는 생성자에 Fake/InMemory를 직접 주입한다. Spring context나 Docker 실행을 강제하지 않는다. fixture의 컴파일 경로에 Spring/JPA 라이브러리가 전혀 없다는 뜻은 아니다. 실제 파일·DB·Redis·트랜잭션을 확인하는 검사는 통합 테스트로 구분한다. MinIO를 쓰는 storage 7개 사례도 integration으로 분류했다.

Fake는 반환값만 맞추지 않는다. 소유자 일치·불일치·미존재, 필터·정렬·갱신·삭제·페이징과 예외 계약을 재현한다. 포트를 바꾸면 구현과 Fake 소비자를 함께 확인한다. publisher Fake는 payload·횟수·조건을 검사하며 AFTER_COMMIT이나 rollback 동작을 입증하지는 않는다.

## Status(상태)

Accepted(승인됨)

- Implementation Record(적용 기록): 사용자가 위임한 구현 범위에서 2026.11.17에 적용했다. 현재 작업 트리는 미커밋 상태다.
- 검증 근거: 최종 빌드 검사자의 결과를 읽어 확인했다. 지정한 로컬 사례 2,346개 중 2,345개 통과, 기존 성능 측정 1개 건너뜀, 남은 실패·오류 0개다. 이 문서 작성자는 Gradle을 실행하지 않았다.
- 검증 입력은 서브모듈 `e1beb652`의 SQL 32개 snapshot이다. 생성 리소스는 기존 로컬 SQL 30개 상태로 복원했다. 로컬 SQL 30개로 같은 검사가 통과했다는 뜻은 아니다. 기존 dirty gitlink는 보존했다.
- 원격 CI, 배포, 전체 성능, 선택하지 않은 전체 테스트는 미검증이다.

## Consequences(결과와 영향)

업무 fixture를 선택해 사용할 수 있고 운영 main과 bootJar에는 넣지 않는다. 최종 검사자는 main과 fixture 의존 순환 0, fixture 재노출 0, 세 bootJar의 업무 fixture·테스트 도구 혼입 0을 확인했다. Review/User 저장소 Fake는 실제 테스트 경로에서 각 소유자의 fixture jar 한 벌이 선택됐다.

fixture별 의존을 관리하는 비용이 생긴다. 여러 업무를 묶는 Factory는 앱에서 조립해야 한다. 순수 Fake 검사가 실제 DB·잠금·이벤트 전달을 모두 검증하는 것은 아니다. 모듈 구성은 [업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다](<2026.11.17 업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다.md>), 계약과 이벤트는 [모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다](<2026.11.17 모듈 간 협력은 공개 계약과 단방향 의존으로 구성한다.md>)를 따른다.
