# ADR: 검색 결과 ID 집합은 정렬 방식과 무관하게 같아야 하며 인기순은 스냅샷 없는 주류를 0점으로 포함한다

- 상태: 적용됨 (커밋 `9186c312`)
- 결정일: 2026.09.05
- 대상: `bottlenote-mono` alcohols 도메인(`CustomAlcoholQueryRepositoryImpl`, `AlcoholQueryService`, `ExploreStandardCriteria`), `bottlenote-product-api`
- 관련 이슈: `bottle-note/workspace#438`
- 원본 계획: `plan/2026.09.05 검색 결과 개수 일치.md` (git 히스토리)

## 결정

- 같은 데이터와 필터에서는 정렬 방식과 페이지 크기에 관계없이 둘러보기 검색의 전체 주류 ID 집합이 동일해야 한다.
- 인기순(POPULAR) 후보 조회는 최신 HOUR 인기도 스냅샷을 INNER JOIN하지 않고 LEFT JOIN + `COALESCE(score, 0)`으로 스냅샷 없는 주류를 0점으로 포함한다. 누락 점수는 조회 정렬에서만 0으로 취급하며 DB나 배치에 점수를 만들어 넣지 않는다.
- 스냅샷이 전혀 없을 때도 검색한다. 첫 페이지의 스냅샷 부재를 서명된 cursor에 `bucketAt=NONE`으로 기록해, 조회 도중 첫 스냅샷이 생겨도 다음 페이지가 기존 기준을 유지한다. 기존 날짜형 `bucketAt` cursor는 계속 해석하고, 잘못된 날짜·누락 `bucketAt`은 기존 `INVALID_CURSOR` 처리다.
- 0점 동점은 ASC/DESC 모두 ID 오름차순 tie-breaker로 중복·누락 없이 seek한다. 필터, 삭제 제외, 평점 범위 규칙은 유지한다.

## 배경

운영 API에서 "벤로막" 검색이 POPULAR 31개, RANDOM 34개로 달랐다. 인기순에만 있는 최신 HOUR 스냅샷 INNER JOIN이 검색 대상을 제한한 것이다. 인기도 롤업 구조(2026.08.23 ADR)에서 시간 관측은 조회가 발생한 주류만 저장하는 희소 저장이므로, 스냅샷이 없는 주류는 "인기도 0"이지 "검색 대상 아님"이 아니다.

## 선택하지 않은 대안

- 배치가 모든 주류에 0점 스냅샷을 채움: 희소 저장 원칙을 깨고 저장량이 늘어난다.
- 인기순에서만 결과가 적은 것을 문서화: 정렬을 바꿨는데 결과 수가 달라지는 것은 사용자 관점의 결함이다.

## 결과와 비용

- 스냅샷 부재를 cursor에 인코딩하므로 cursor context 종류가 하나 늘었다.
- 회귀 테스트는 34개 중 31개 스냅샷 재현, 페이지 크기 10/20 전체 목록 비교, 0점 ASC/DESC 동점, 전체 스냅샷 부재와 첫 스냅샷 생성, 평점·삭제 필터, 잘못된 cursor를 GitHub Actions에서 실행한다.
- 프론트엔드와 요청 파라미터 수정은 범위 밖이다.
