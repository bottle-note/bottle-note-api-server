# ADR: Redis Sentinel 연결은 개발 환경부터 적용하고 Sentinel·데이터 노드 인증을 분리한다

- 상태: 적용됨
- 결정일: 2026.08.23
- 대상: `bottlenote-mono` `RedisConfig`·`LettuceClientSupport`, `bottlenote-product-api`, `bottlenote-admin-api`, `bottlenote-batch`, `git.environment-variables`(개발 Secret)
- 관련 PR: `bottle-note/bottle-note-api-server#727`(batch failover 재연결)
- 원본 계획: `plan/Redis Sentinel 연결 지원.md` (git 히스토리)

## 결정

- 공통 `RedisConfig`가 `REDIS_MODE`에 따라 `standalone`, `cluster`, `sentinel` 연결을 만든다. Sentinel master group은 `bottlenote-master`, 노드는 개발 클러스터 headless Service DNS 3개다.
- Sentinel 탐색 인증(username/password)과 Redis 데이터 노드 인증을 별도 Spring Boot 공식 속성으로 바인딩한다. 개발에서는 같은 비밀번호를 쓰지만 속성은 분리한다. 기존 `REDIS_HOST`, `REDIS_PORT` 의존은 제거한다.
- Sentinel mode는 `ReadFrom.MASTER`로 Lettuce의 Sentinel topology refresh를 활성화한다. lookup·access-control 전용 Lettuce factory도 Sentinel 구성과 기존 2초/200ms timeout 정책을 보존하며 command/connect timeout을 분리한다. TCP keepalive, TCP_USER_TIMEOUT, 반열림 복원력 설정은 유지한다.
- batch는 Boot Redis auto-configuration에 Sentinel topology와 공용 socket 복원력 customizer를 적용한다. 개발 failover 검증에서 product/admin은 정상 전환했으나 batch의 공유 연결이 이전 master에 고착돼 READONLY가 재현됐기 때문이다. batch standalone에서는 빈 Sentinel/cluster 바인딩을 만들지 않는다.
- 운영 환경은 이번 변경 대상이 아니며 기존 연결 방식을 유지한다.
- 도메인 코드(인기도 등)는 topology를 알지 않고 공통 `RedisTemplate`만 주입받는다.

## 배경

개발 Redis의 장애 전환을 애플리케이션이 직접 인식하지 못해 failover 후 이전 master로 계속 붙는 문제가 있었다. 로컬 포트포워드만으로는 Sentinel이 반환하는 클러스터 내부 master 주소까지 라우팅할 수 없어, Sentinel 인증·master 조회 검증과 실제 backend 연결 검증을 분리해 클러스터 네트워크 안에서 확인했다.

## 선택하지 않은 대안

- 애플리케이션 수준 재연결 폴링: Lettuce의 Sentinel topology refresh가 표준 경로다.
- 운영 동시 전환: 개발에서 failover 동작을 먼저 확인한 뒤 판단한다.

## 결과와 비용

- Sentinel은 가용성을 높이지만 비동기 복제 구간의 쓰기 유실을 막지 않는다. Redis 카운터 같은 값은 best-effort로 정의한다(인기도 ADR 6.4).
- 개발 Secret은 Sentinel 환경변수를 평문 노출 없이 제공하도록 SOPS Secret 2개를 전환했다.
