# 중복 위스키는 기준 위스키로 합친 뒤 삭제하고 되돌리지 않는다

- Decision Date(결정일): 2026.11.10
- Scope(대상): Admin 위스키 병합 API(`/alcohols/merges`), 위스키 ID를 저장하는 테이블의 데이터 이동, 병합 로그, 인기도 관측 배치
- Related Issue(관련 이슈): bottle-note/workspace#543
- Related PRs(관련 PR): [삭제된 위스키의 연관 데이터를 조회에서 제외 #818](https://github.com/bottle-note/bottle-note-api-server/pull/818), [중복 위스키 병합 Admin API 추가 #819](https://github.com/bottle-note/bottle-note-api-server/pull/819), 스키마 bottle-note/environment-variables#44, bottle-note/environment-variables#45

## Context(배경)

같은 위스키가 두 번 등록되면 리뷰, 별점, 찜이 두 위스키에 나뉘어 쌓인다. 기존 삭제 API는 리뷰나 별점이 있는 위스키를 거절하므로 중복을 정리할 방법이 없었다.

이 문서에서 남기는 위스키를 기준 위스키, 합쳐서 없애는 위스키를 중복 위스키라고 부른다. API와 테이블에서는 각각 `base`, `duplicate`로 쓴다.

위스키 ID는 review, rating, picks, history, mfds, alcohols 도메인의 여러 테이블에 저장되고 대부분 FK가 없다. 병합에서 한 테이블이라도 빠뜨리면 없는 위스키를 가리키는 행이 남는데, 오류가 나지 않아 알아채기 어렵다.

레이어 표준 6은 다른 도메인의 repository와 service를 직접 참조하지 못하게 한다. rating, picks, history, mfds에는 Facade가 없고, 기존 레포지토리 인터페이스에 메서드를 더하면 그 인터페이스를 구현한 테스트용 InMemory 구현을 모두 고쳐야 한다.

같은 사용자가 두 위스키에 모두 별점이나 찜을 남긴 경우처럼 그대로 옮길 수 없는 데이터도 있다.

## Decision(결정)

### Per-domain Move(도메인별 데이터 이동)

alcohols 도메인에 `AlcoholMergeHandler` 인터페이스를 둔다. 위스키 ID를 저장하는 테이블을 가진 도메인은 `{domain}.repository`에 구현 클래스를 하나씩 두고, 자기 테이블의 행을 중복 위스키에서 기준 위스키로 옮긴다. 병합 서비스는 구현 클래스 목록을 주입받아 모두 실행하며 실행 순서는 결과에 영향을 주지 않는다.

alcohols는 다른 도메인의 클래스를 참조하지 않는다. 위스키 ID 컬럼을 새로 만드는 도메인은 구현 클래스를 추가해야 한다.

### Merge Rules(병합 규칙)

- 기준 위스키 1개에 중복 위스키를 최대 10개까지 한 트랜잭션으로 합친다. 하나라도 실패하면 전부 취소한다.
- 병합에 포함된 위스키 행을 ID 순서로 잠근다. 같은 중복 위스키를 병합하는 요청이 동시에 오면 하나만 성공한다.
- 삭제 표시된 위스키는 기준으로도 중복으로도 쓸 수 없다. 삭제된 위스키를 합치면 숨겨져 있던 찜과 히스토리가 기준 위스키에 다시 노출되기 때문이다.
- 기준 위스키의 이름, 이미지, 설명은 바꾸지 않는다.
- 리뷰와 활동 히스토리는 모두 옮긴다. 히스토리의 위스키 링크와 베스트 리뷰 선정 로그의 위스키 ID도 기준 위스키로 바꾼다.
- 같은 사용자의 별점, 찜, 최근 본 기록이 두 위스키에 모두 있으면 기준 위스키의 기록을 남기고 중복 위스키의 기록을 삭제한다.
- 예외: 기준 위스키의 기록이 0점 별점(사용자가 지운 별점)이거나 해제된 찜이고 중복 위스키의 기록이 유효하면, 기준 위스키의 기록을 삭제하고 중복 위스키의 기록을 옮긴다. 0점과 해제는 사용자에게 기록이 없는 상태이므로, 이 예외가 없으면 사용자의 실제 별점과 찜이 사라진다.
- 테이스팅 태그, 큐레이션 키워드, 값을 여러 개 가질 수 있는 속성은 두 위스키의 것을 합친다. 값을 하나만 가지는 속성은 기준 위스키의 값을 유지한다.
- 수입 신고는 확정된 연결(`selected_alcohol_id`)만 옮긴다. 후보와 과거 매칭 기록은 당시 판단의 근거이므로 바꾸지 않는다.
- 데이터를 모두 옮긴 뒤 중복 위스키 행을 실제로 삭제한다. 삭제 표시(`deleted_at`)만 한 행을 남기지 않는다.
- 인기도 관측과 스냅샷은 옮기지 않는다. 중복 위스키 행을 지울 때 FK(`ON DELETE CASCADE`)로 함께 지워지고, 기준 위스키의 값은 배치가 다시 계산한다.
- 이미 병합된 위스키는 존재하지 않으므로 다시 병합하면 `ALCOHOL_NOT_FOUND`다.

### Preview(미리보기)

미리보기는 병합을 실제로 실행한 뒤 트랜잭션을 롤백하고, 실행하면서 얻은 건수를 돌려준다. 건수를 세는 쿼리를 따로 두지 않으므로 미리보기와 병합의 건수가 달라질 수 없다. 미리보기와 병합 사이에 데이터가 바뀌면 병합은 바뀐 데이터로 다시 계산한다.

건수는 대상별로 옮긴 건수(`moved`)와 삭제한 건수(`deleted`)다. 삭제한 건수에는 중복 위스키에서 삭제한 행과 위 예외로 기준 위스키에서 삭제한 행이 모두 들어간다.

### No Undo(되돌리기 없음)

병합을 되돌리는 기능은 두지 않는다. 삭제한 행과 중복 위스키 행은 복구할 수 없다. `alcohol_merge_logs`에 중복 위스키 한 건당 한 행으로 병합 시점의 이름, 대상별 건수, 처리한 관리자와 시각을 남기고 조회만 제공한다.

### Rejected Alternatives(선택하지 않은 대안)

- 도메인마다 Facade를 새로 만드는 방식: 도메인마다 인터페이스, 구현 클래스, 테스트용 Fake가 필요해 코드가 몇 배로 늘어난다.
- alcohols 도메인의 레포지토리 하나가 모든 테이블을 고치는 방식: 코드는 가장 적지만 alcohols가 다른 도메인의 테이블 구조를 알게 된다.
- 미리보기용 집계 쿼리를 따로 두는 방식: 병합 규칙이 바뀔 때마다 두 곳을 함께 고쳐야 한다.
- 중복 위스키 행에 삭제 표시만 하는 방식: 삭제된 위스키와 병합된 위스키가 같은 모습으로 남아 구분하기 어렵다.

## Status(상태)

Accepted(승인됨)

## Consequences(결과와 영향)

- 위스키 행이 실제로 지워질 수 있게 됐다. 인기도 관측 테이블은 `alcohols`에 FK가 걸려 있어, 없는 위스키 ID를 저장하려 하면 그 관측 단계 전체가 실패한다. 그래서 배치의 `ObservationWriter`가 존재하지 않는 위스키의 행을 빼고 저장한다. batch는 따로 배포하므로 병합 API를 쓰기 전에 batch를 먼저 배포해야 한다.
- 병합 SQL은 MySQL의 다중 테이블 `DELETE`와 `UPDATE ... JOIN`을 쓴다. 통합 테스트로만 검증된다.
- 병합은 `user_histories`, `alcohols_view_histories`, `curation_keyword_alcohol_ids`에서 위스키 ID로 행을 찾는다. 전체 스캔을 피하도록 V33에서 세 테이블에 위스키 ID 인덱스를 추가했다.
- 로그 테이블은 V32에서 `target`, `source` 컬럼으로 만들었다가 V34에서 `base`, `duplicate`로 이름을 바꿨다.
- 미리보기도 쓰기 트랜잭션이므로 실행하는 동안 관련 행에 잠금이 걸린다.
- 중복 위스키의 이름 외 정보(설명, 이미지, 도수 등)는 병합과 함께 사라진다. 필요한 값은 병합 전에 기준 위스키에 옮겨 적어야 한다.
- 큐레이션 payload(JSON)와 수입 신고의 과거 매칭 기록에 들어 있는 위스키 ID는 고치지 않는다. 병합 뒤에는 없는 ID가 되며, 큐레이션에서는 그 위스키가 빠진다. 관리자가 직접 수정해야 한다.
- 병합이 끝나는 순간에 사용자가 중복 위스키에 별점이나 찜을 쓰면 그 한 건이 없는 위스키를 가리킨 채 남는다. 사용자 쓰기 경로는 위스키 행을 잠그지 않기 때문이다. 조회는 위스키와 조인하므로 이 행은 노출되지 않고, 배치도 이 행을 뺀다.
- 찜 테이블에는 유니크 제약이 없다. 중복 위스키에 같은 사용자의 찜이 여러 행 있으면 모두 옮겨진다.
- Redis의 최근 본 위스키와 조회수 키는 정리하지 않는다. DB로 동기화되어도 없는 위스키의 데이터라 노출되지 않는다. 자동완성 스냅샷에는 다음 동기화(기본 5분)까지 병합된 위스키가 남는다.
