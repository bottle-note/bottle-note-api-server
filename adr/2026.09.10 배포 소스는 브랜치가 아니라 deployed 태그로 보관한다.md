# 배포 소스는 브랜치가 아니라 deployed 태그로 보관한다

- Decision Date(결정일): 2026.09.10
- Scope(대상): bottle-note-api-server, admin-dashboard, bottle-note-frontend의 릴리즈 파이프라인

## Context(배경)

Release PR 경로는 일회용 릴리즈 브랜치를 만들고, 배포가 끝나면 그 브랜치를 지운다. 표준 릴리즈에서는 배포 소스가 main에 쌓인 빈 커밋이므로 브랜치를 지워도 main이 그 커밋을 계속 붙잡는다. 따라서 브랜치 정리 자체는 안전하다.

핫픽스는 다르다. 핫픽스의 배포 소스는 hotfix PR의 병합 커밋인데, 자동 역병합이 없으므로 이 커밋은 main에 올라가지 않는다. 핫픽스 브랜치를 지우면 그 커밋에 도달하는 참조가 하나도 남지 않는다. 다음 핫픽스는 직전 운영 배포 소스에서 잘라야 하므로, 도달 불가능한 커밋을 기준점으로 삼아야 하는 상태가 된다.

기존 구현은 이 문제를 우회하려고 배포 기준점을 Actions 실행 이력에서 역추적했다. 성공한 실행 목록을 페이지 단위로 훑고, 각 실행의 job 이름을 하드코딩된 목록과 대조하고, 병합된 PR을 15분 시간 창으로 맞추는 방식이었다. 이 로직은 job 이름 변경에 취약하고, 실행 보존 기간에 의존하며, 세 레포에 복제하기 어려울 만큼 길었다.

세 서비스 레포는 같은 릴리즈 계약을 공유해야 하지만, 핫픽스 경로는 admin-dashboard에만 있었고 릴리즈 키 재사용 방어와 병합 검증 강도도 레포마다 달랐다.

## Decision(결정)

배포에 성공한 소스에 annotated 태그 `deployed/<배포 단위>/<YYYY-MM-DD>/<N>`을 찍고, 이 태그를 배포 이력의 단일 기준으로 삼는다.

### 태그 계약

- 태그는 배포 단위마다 하나다. 단위는 dashboard, frontend, product, admin이며 백엔드는 배포 모드에 따라 한 릴리즈에서 태그를 하나 또는 둘 만든다.
- 태그 생성은 배포 job이 성공한 뒤, 릴리즈 브랜치를 지우기 전에 실행한다. 순서가 뒤바뀌면 참조가 끊긴 구간이 생긴다.
- 태그는 릴리즈 키당 하나이며 덮어쓰지 않는다. 생성 직후 되읽어 배포 소스를 가리키는지 확인한다.
- 릴리즈 키 재사용은 브랜치 부재, 레지스트리 이미지 태그 부재, deployed 태그 부재 세 가지로 막는다. 브랜치는 배포 후 삭제되고 이미지 태그는 레지스트리에 의존하므로, deployed 태그가 최종 방어선이다.

### 핫픽스 기준점

핫픽스 브랜치는 해당 배포 단위의 최신 deployed 태그가 가리키는 커밋에서 자른다. Actions 실행 이력은 더 이상 조회하지 않는다. 백엔드처럼 배포 단위가 둘인 경우, 모든 단위의 최신 태그가 같은 릴리즈 키와 같은 커밋을 가리킬 때만 핫픽스를 시작할 수 있다.

### 세 레포 동일성

브랜치 네임스페이스, 릴리즈 키 규칙, PR 본문 마커 계약, 검증 단계와 순서, 태그 규칙, 워크플로 파일명, job 이름을 세 레포가 공유한다. 서비스 식별자와 이미지 개수, 빌드 스텝만 다르다.

공유 로직은 `# >>> common <이름>`과 `# <<< common <이름>` 주석으로 감싸고, `.github/scripts/verify_pipeline_blocks.sh`가 블록 해시를 `.github/scripts/pipeline_blocks.sha256`의 기대값과 대조한다. 한 레포에서 블록을 고치면 세 레포를 모두 고쳐야 통과한다. 현재 공유 블록은 배포 태그 조회, 배포 태그 생성, 후보 CI 검증, PR 메타데이터 검증 네 가지다.

레포마다 다를 수밖에 없는 값은 환경변수로만 분리한다. 배포 단위는 `DEPLOYED_SERVICES`, 핫픽스 후보에 요구하는 체크 이름은 `REQUIRED_CI_CHECKS`가 담는다.

### Rejected Alternatives(선택하지 않은 대안)

릴리즈 브랜치를 지우지 않고 남기는 방안은 기준점 문제를 풀지만, 브랜치 네임스페이스가 릴리즈 횟수만큼 늘어나고 어느 브랜치가 현재 운영인지가 이름만으로는 드러나지 않는다. 태그는 같은 보존 효과를 주면서 브랜치 목록을 비워 둔다.

공유 로직을 조직 레포의 reusable workflow로 옮기는 방안은 동일성을 가장 강하게 보장하지만, 별도 레포와 권한 설계가 필요하고 되돌리기 어렵다. 블록 해시 대조로 먼저 동일성을 강제하고, reusable workflow 전환은 후속 과제로 남긴다.

## Status(상태)

Accepted(승인됨)

### Implementation Record(적용 기록)

세 레포의 릴리즈 워크플로에 태그 생성과 태그 기반 핫픽스 기준점을 적용했다. 백엔드 워크플로 파일명에서 `pilot`을 제거해 세 레포 이름을 통일했고, admin-dashboard에만 있던 핫픽스 경로를 나머지 두 레포로 전파했다. cosign-installer는 세 레포 모두 v4.1.2로 맞췄다.

검증은 YAML 파싱, 워크플로에서 추출한 셸 블록의 문법 검사, 공통 블록 해시 대조까지 수행했다. 태그 생성과 핫픽스 경로의 실제 실행 검증은 하지 않았다. 핫픽스 워크플로는 세 레포 모두 실행 이력이 0건이다.

태그가 없는 상태에서는 핫픽스를 시작할 수 없다. 도입 시점에 현재 운영 소스로 소급 태그를 찍어 부트스트랩한다.

## Consequences(결과와 영향)

핫픽스 기준점이 Actions 실행 보존 기간과 job 이름에서 독립한다. 기준점 탐색 코드가 크게 줄어 세 레포에 같은 형태로 복제할 수 있게 됐다.

배포 이력이 태그 목록으로 드러나므로, 어떤 릴리즈 키가 어느 커밋으로 나갔는지 저장소만 보고 알 수 있다. 릴리즈 키 재사용도 영구 기록으로 막힌다.

반대로 태그가 배포 파이프라인의 필수 상태가 된다. 태그 생성이 실패하면 릴리즈가 실패로 끝나고, 배포 단위가 여럿일 때 일부만 태그된 상태로 멈출 수 있다. 이 경우 남은 태그를 수동으로 정리해야 다음 릴리즈가 같은 키를 쓸 수 있다.

태그를 사람이 임의로 지우거나 옮기면 핫픽스 기준점이 어긋난다. deployed 네임스페이스는 파이프라인만 쓰는 것으로 취급한다.
