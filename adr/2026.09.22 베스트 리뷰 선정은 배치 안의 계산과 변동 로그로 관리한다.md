# ADR: 베스트 리뷰 선정은 배치 안의 계산과 변동 로그로 관리한다

- Decision Date(결정일): 2026.09.22
- Scope(대상): `bottlenote-batch`, `bottlenote-mono`, `bottlenote-admin-api`, `git.environment-variables`
- Related Documents(관련 문서): [인기도 관측은 시간·주·월 롤업 구조로 관리한다](<2026.08.23 인기도 관측은 시간·주·월 롤업 구조로 관리한다.md>), [batch는 독립 상주 애플리케이션으로 운영한다](<2026.01.22 batch는 독립 상주 애플리케이션으로 운영한다.md>)

## Context(배경)

베스트 리뷰는 매일 자정 배치가 `reviews.is_best`를 갱신해 정한다. 기존 구현은 서브모듈의 `storage/mysql/sql/best-review-selected.sql`을 클래스패스로 패키징해 Chunk 리더가 읽고, 앞 단계에서 전체 `is_best`를 `FALSE`로 초기화한 뒤 결과를 `TRUE`로 썼다.

2026.09.22 운영·개발 DB를 확인한 결과 베스트 리뷰가 한 건도 없었다. 리더가 첫 실행의 결과 목록과 인덱스를 인스턴스 필드에 보관해 파드 기동 후 첫 자정에만 읽고 그 뒤로는 빈 결과를 돌려줬다. 초기화 단계는 매일 실행되므로 둘째 날부터 모든 베스트 표시가 사라졌다. Job 상태는 `COMPLETED`라 로그로는 드러나지 않았고 `BATCH_STEP_EXECUTION`의 `READ_COUNT`가 0인 것으로만 확인됐다.

선정 SQL에도 문제가 있었다. 좋아요·댓글·이미지를 한 쿼리에서 LEFT JOIN 하고 집계해 행이 곱해졌고, 삭제·비공개 리뷰도 후보와 리뷰 수에 포함됐다. 왜 특정 리뷰가 선정됐는지 남는 기록이 없어 관리자가 문의에 답할 수 없었다.

## Decision(결정)

베스트 리뷰 선정을 배치 안의 Java 계산으로 옮기고, `is_best` 변동마다 사유를 로그로 남긴다.

- 서브모듈의 `storage/mysql` 디렉터리를 제거한다. 배치는 서브모듈에서 어떤 리소스도 패키징하지 않으며, 서브모듈은 `storage/db/migration`만 스키마 원본으로 제공한다. `verifyBatchPackagedResources` 태스크는 검사 대상이 사라져 함께 제거한다.
- 선정 규칙은 `BestReviewSelectionRule`의 순수 함수로 둔다. 2026.09.22 운영 데이터(ACTIVE·PUBLIC 리뷰 193건, 좋아요 최대 6개, 리뷰 3건 이상 주류 13종)를 기준으로 옛 규칙을 다음처럼 바꾼다.
  - 후보 조건: 주류 리뷰 2건 이상, 순좋아요(좋아요 − 싫어요) 1 이상, 본문 30자 이상을 모두 만족한다. 옛 규칙의 "혼자 있어도 좋아요 5개면 선정"과 "리뷰 3건이면 좋아요 0이어도 선정"을 없앤다.
  - 점수: 순좋아요 0.6 + 작성자 본인을 뺀 서로 다른 댓글 작성자 수(최대 5명) 0.2 + 이미지 보유 0.2. 싫어요 −0.1 가중은 순좋아요로 대체한다.
  - 선정 수: 리뷰 수 10건 미만 1건, 10~19건 2건, 20건 이상 3건은 유지한다.
  - 동점: 최신 리뷰(ID 내림차순)가 앞선다. 오래된 리뷰가 베스트에 고착되는 것을 막는다.
  - 시간 가중은 두지 않는다. 로그에 판정 수치가 남으므로 몇 달치 데이터를 본 뒤 반감기 도입을 다시 판단한다.
- 후보는 ACTIVE·PUBLIC 리뷰만이고 주류 리뷰 수도 같은 기준으로 센다. 좋아요·댓글·이미지는 리뷰별로 따로 집계해 메모리에서 합쳐 카티전 곱을 없앤다.
- 전체 초기화 단계를 없앤다. 실행마다 이번 선정 집합과 현재 `is_best` 집합의 차이만 갱신하므로 변동 없는 날과 재실행은 아무것도 바꾸지 않는다.
- 변동은 `best_review_selection_logs`에 선정(`SELECTED`)과 해제(`RELEASED`)로 남긴다. 판정 시점의 순위·점수·좋아요·싫어요·댓글 작성자 수·이미지 수·본문 글자 수·주류 리뷰 수, 적용 규칙 코드, 사람이 읽는 사유를 함께 저장한다. 유일성은 `(selection_date, review_id, change_type)`이며 재실행은 같은 행을 덮어쓴다. 시계열 관측이 아니라 변동 기록이므로 유지되는 날에는 행을 만들지 않는다.
- 관리자 API `GET /reviews/best-selection-logs`가 로그를 페이지로 내린다. 쓰기는 배치가 JDBC로 하고 mono의 엔티티는 조회와 스키마 검증에만 쓴다.
- Quartz Job 키 `bestReviewSelectedJob`과 자정 스케줄은 유지한다. 기존 JDBC JobStore 행을 그대로 쓰기 위해서다.

### Rejected Alternatives(선택하지 않은 대안)

- 리더만 `@StepScope`로 고쳐 기존 SQL과 규칙을 유지: 카티전 곱과 비활성 리뷰 포함 문제, 혼자 있는 리뷰가 베스트가 되는 문제, 사유 기록 부재가 남는다.
- 인기도처럼 시간·주·월 시계열로 관측: 베스트 리뷰는 하루 한 번 정해지는 상태이고 요구는 변동 사유 조회다. 롤업과 정리 규칙이 필요 없다.
- 로그를 `is_best` 갱신과 분리해 별도 트랜잭션으로 기록: 갱신은 됐는데 로그가 없는 상태가 생긴다. 한 Tasklet 트랜잭션 안에서 함께 쓴다.

## Status(상태)

Accepted(승인됨)

## Consequences(결과와 영향)

- 파드 재시작과 무관하게 매일 선정이 갱신된다. 첫 실행은 현재 `is_best`가 전부 `FALSE`이므로 선정 대상 전체를 `SELECTED`로 기록한다.
- 배치 이미지는 서브모듈 내용을 포함하지 않는다. 배치 빌드가 서브모듈 초기화에 의존하지 않는다.
- 스키마는 V20이 추가하며 제품·어드민 기동이 적용한다. 배치 배포는 V20 적용 뒤여야 한다.
- 관리자 화면은 로그 목록으로 특정 리뷰가 언제 왜 선정·해제됐는지 답할 수 있다. 판정 수치는 그날 배치 시점의 값이며 현재 값과 다를 수 있다.
