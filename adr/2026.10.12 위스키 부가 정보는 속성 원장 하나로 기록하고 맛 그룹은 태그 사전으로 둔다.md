# 위스키 부가 정보는 속성 원장 하나로 기록하고 맛 그룹은 태그 사전으로 둔다

- Decision Date(결정일): 2026.10.12
- Scope(대상): `alcohols` 도메인의 `alcohol_attributes`, `tasting_tag_groups`, `tasting_tag_group_tags`와 바텐더 노트 추천이 읽는 데이터
- Related(관련): environment-variables PR #34 (V24 마이그레이션)

## Context(배경)

바텐더 노트(위스키 추천) 프로토타입은 술 665종의 키워드·대중성·가격과, 테이스팅 태그를 결 축으로 묶은 사전을 HTML 안에 데이터와 정규식으로 박아 두고 있다. 이를 서버가 소유하려면 어디에 어떤 모양으로 둘지 정해야 했다. 처음 안은 가격 원장, 대중성 원장, 술별 추천 프로필, 키워드 사전과 매핑, 키워드 엣지, 술×그룹 점수까지 테이블 7개였고, 운영자가 관리할 것이 너무 많다는 판단으로 줄였다.

제약은 다음과 같다. 키워드·가격·대중성은 출처와 기준 시점이 함께 남아야 하고, 키워드 종류는 운영 중에 계속 늘어나며, 그래프(노드·엣지)로 노출하고 싶다. 대중성의 외부 원천(데일리샷)은 제휴 전에는 반복 수집이 불가능하다.

## Decision(결정)

- 술 부가 정보는 `alcohol_attributes` 한 테이블에 EAV로 기록한다. `attribute_key`는 자유 문자열, `attribute_type`(KEYWORD·POPULARITY·PRICE·FLAG·IDENTITY·NOTE)과 `datatype`(STRING·INT·DOUBLE·BOOLEAN)만 고정 코드다. 값은 문자열로 저장하고 datatype으로 검증·변환한다. `description`에 근거·출처, `based_at`에 기준 시점을 남긴다. (alcohol_id, key, value)는 유일하다.
- `alcohols` 테이블은 바꾸지 않는다. 도수 구간 같은 파생값도 속성 행으로 둔다.
- 맛 그룹은 `tasting_tag_groups` 사전과 `tasting_tag_group_tags` 연결(role CORE 1.0 / PERIPHERAL 0.4)로 둔다. 연결은 그룹 애그리게이트가 소유하며 JPA `@ElementCollection`으로 통째 저장한다. `family`(위스키 계열)는 enum이 아니라 자유 문자열이다.
- 술×그룹 점수, 키워드 사전·매핑 테이블, 키워드 엣지, 가격·대중성 별도 원장, 술별 추천 프로필은 만들지 않는다. 그래프 엣지는 같은 술에 같이 붙은 키워드의 동시 출현으로 계산하고, 결 점수는 `alcohols_tasting_tags`와 그룹 연결을 요청 시점에 겹쳐 계산한다.
- 서버는 영문 코드만 다루고 한글 표기는 화면이 붙인다. 어드민 API 경로는 하이픈 없이 뎁스로 둔다(`/alcohols/attributes`, `/tasting/groups`).

### Rejected Alternatives(선택하지 않은 대안)

- 키워드를 `alcohols` json 배열 컬럼으로: 출처·시점을 못 남기고 그래프 집계에 JSON_TABLE이 필요하다.
- 키워드 사전 + 매핑 테이블: 매핑은 속성 행으로 대체되고, 사전은 입력된 값의 distinct로 충분하다. 필요가 생기면 승격한다.
- `STRING_REGEX` datatype과 행별 pattern 컬럼: 검증 규칙이 데이터에 섞여 폐기했다.
- 엔티티를 `entity_type + entity_id`로 추상화: 외래키를 잃고 조회·검증이 어려워져 술 전용으로 둔다.

## Status(상태)

Accepted(승인됨). 스키마는 environment-variables PR #34로 병합했고, 엔티티·포트·JPA 구현·InMemory 더블은 메인 저장소 PR에서 추가한다. 서비스·어드민 API·시드 적재는 후속이다.

## Consequences(결과와 영향)

- 긍정: 테이블 3개로 시작하고 키워드 종류·계열이 늘어도 스키마가 바뀌지 않는다. 출처와 시점이 행마다 남아 데이터 신뢰도를 화면에서 설명할 수 있다.
- 부정: 값이 문자열이라 숫자 비교·정렬은 애플리케이션이 변환해야 하고, 키워드 표기 불일치("60도 이상" vs "60도이상")를 DB가 막지 못한다. 화면의 기존 값 자동완성으로 완화한다.
- 중립: 추천 결 점수를 저장하지 않으므로 요청마다 계산한다. 후보가 수백 종이라 비용은 작지만, 커지면 읽기 모델을 추가한다.
