# ADR: 알림은 Notification SSOT와 의미 기반 Action 계약으로 제공하고 Delivery는 분리한다

- 상태: 적용됨
- 결정일: 2026.08.10 (푸시 제거 2026.05.14, SSOT·알림함 API 2026.08.08, Action 계약 2026.08.10)
- 대상: `bottlenote-mono` notification 도메인, `bottlenote-product-api`, `git.environment-variables`(V10)
- 관련 이슈·PR: `bottle-note/workspace#311`, `#381`, `bottle-note/bottle-note-api-server#701`, `#704`
- 원본 계획: `plan/complete/remove-push-feature.md`, `plan/notification-push-system.md`, `notification-action-ms1-2.md` (git 히스토리)

## 결정

- `Notification`은 "무엇을 누구에게 알릴 것인가"의 SSOT다. Delivery(SSE, Mobile Push)는 채널별로 독립 판정하는 별개 책임이며 Delivery 채널이 없어도 알림은 DB에 남아 알림함(`/api/v1/notifications`)에서 조회된다. Web Push는 쓰지 않는다.
- Firebase FCM 발송·디바이스 토큰 저장·`/api/v1/external/push/**`는 제거했다. 하드코딩된 대상 사용자와 인증 경계 밖 엔드포인트가 운영 위험이었고 제품상 필요가 사라졌다. `user_device_tokens`, `user_push_configs` 테이블 drop은 후속 마이그레이션이다.
- 읽음 여부의 호환 SSOT는 `is_read`, `read_at`은 최초 읽음 시각이다. 단건·전체 읽음 재호출에도 최초 시각을 유지한다. 전달 `status`(PENDING/SENT/FAILED)는 읽음과 무관하게 보존하고 신규 `READ`를 기록하지 않는다.
- 알림 클릭 이동은 별도 실행 endpoint 없이 목록 응답의 의미 기반 Action(`OPEN_REVIEW`, `OPEN_HELP`, fallback `OPEN_NOTIFICATION_CENTER`)으로 표현한다. 서버와 DB에 URL, Universal Link, 앱·웹 route 문자열을 저장하지 않는다. 앱·웹이 각자 내부 route로 변환한다.
- Action은 typed DTO(`action_type`, `action_target_id`, `action_payload`, `action_version`)로 저장하고, 잘못된 type/version/key/범위/크기(1 KiB 초과) payload는 해당 item만 `action=null`로 강등한다. 목록 전체는 정상 반환한다.
- 이동 시점의 존재·공개·권한 검증은 리뷰 상세·문의 상세 API가 다시 한다. 알림 목록에서 리뷰·댓글 도메인을 N+1로 조회하지 않는다.
- 중복 방지의 최종 방어선은 `(source_type, source_id, user_id)` DB UNIQUE다. 목록은 `id DESC` keyset cursor이며 필터는 `types`, `categories`, `readStatus`, `[createdFrom, createdTo)`다. 시각 입력은 KST로 정규화하고 응답은 `+09:00` offset을 포함한다.
- 1차 생성 트리거는 리뷰 댓글 알림(`REVIEW_REPLY → OPEN_REVIEW`)과 문의 답변 알림(`HELP_ANSWER → OPEN_HELP`)이다. 리스너는 AFTER_COMMIT으로 동작한다.

## 배경

초기 푸시 기능은 검증 없는 공개 엔드포인트와 하드코딩 사용자로 남아 있었다. 알림을 재설계하면서 "알림 사실"과 "전달 채널"을 분리하고, 클라이언트별 라우팅 문자열을 서버가 알지 않도록 계약을 의미 기반으로 정했다. 기존 `notifications` 테이블과 패키지는 drop 후 재생성이 아니라 재사용·진화했다.

## 선택하지 않은 대안

- Action 실행 endpoint: 서버가 클라이언트 라우팅을 알게 되고 앱·웹 배포에 서버가 묶인다.
- 읽음을 `status=READ`로 표현: 전달 상태와 읽음 상태가 섞인다.
- SSE·FCM 1차 도입: Notification SSOT가 먼저다. Phase 2+로 넘겼고 Outbox·채널 envelope 매핑도 그때 한다.

## 결과와 비용

- 향후 SSE/FCM은 같은 canonical Action을 채널별 envelope로 매핑한다. 목록 envelope를 바이트 단위로 복제하지는 않는다.
- V10 인덱스 `(user_id, is_read, id)`, `(user_id, create_at, id)`의 실효성은 운영 분포 `EXPLAIN ANALYZE`로 미검증이다.
- 다중 인스턴스 SSE 라우팅(Redis Pub/Sub)은 Phase 2 이후 과제다.
