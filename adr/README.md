# ADR (Architecture Decision Records)

코드와 git 히스토리에서 복원되지 않는 결정을 기록한다. 계획·진행 상태는 여기에 두지 않는다. 진행 추적은 workspace 이슈와 PR 본문이 담당한다.

## 작성 규칙

- 파일명: `YYYY.MM.DD 결정을 한 문장으로.md`. 날짜는 결정일이며 하이픈을 쓰지 않는다.
- [Michael Nygard의 원형 ADR](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)을 따른다. 제목 아래 본문은 `Context(배경)` → `Decision(결정)` → `Status(상태)` → `Consequences(결과와 영향)` 순서의 네 `##` 항목으로 작성한다.
- 제목은 결정을 한 문장으로 적는다. 제목 아래에는 `Decision Date(결정일)`, `Scope(대상)`, 관련 이슈·PR 등의 메타데이터를 둔다.
- `Context(배경)`: 결정이 필요한 문제, 제약, 충돌하는 요구와 근거를 적는다.
- `Decision(결정)`: 선택한 방식과 이유, 지켜야 할 계약을 적는다. 대안과 제외 이유는 필요할 때 `### Rejected Alternatives(선택하지 않은 대안)`로 보존하며 별도 최상위 항목으로 두지 않는다.
- `Status(상태)`: `Proposed(제안됨)`, `Accepted(승인됨)`, `Deprecated(폐기됨)`, `Superseded(대체됨)` 중 하나를 적는다. 승인과 구현 완료를 구분하며, 기존 `적용됨` 기록과 검증 제한은 `Implementation Record(적용 기록)`로 보존한다. 필요하면 `Revision History(개정 이력)`를 하위 항목으로 둔다.
- `Consequences(결과와 영향)`: 긍정적·부정적·중립적 영향과 비용, 제약, 운영 부담을 적는다.
- 항목명과 메타데이터명은 `English(한글)` 형태로 병기한다. 상세 계약은 해당 본문 항목 아래 `###` 이하로 배치한다. 문서 제목과 본문 문장을 모두 번역할 필요는 없다.
- 결정이 바뀌면 기존 문서를 지우지 않고 `Status(상태)`를 `Superseded(대체됨)`으로 바꾸고 새 문서를 가리킨다. 작은 조정은 개정 이력에 추가한다.
- 2026.09.07 이전 문서는 `plan/` 계획서에서 결정 부분만 추린 것이다. 원본은 각 문서의 `Original Plan(원본 계획)` 항목과 git 히스토리로 찾는다.
