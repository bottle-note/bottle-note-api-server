# admin API를 product 배포 단위로 흡수하고 섀도우 검증 뒤 admin 앱을 제거한다

- Decision Date(결정일): 2026.11.19
- Scope(대상): `bottlenote-product-api`, `bottlenote-admin-api`, admin API의 외부 URL(`/admin/api/**`)과 그 보안 체인·접근 제어·문서·기동 작업
- Related Issue(관련 이슈): bottle-note/workspace#564
- Related ADRs(관련 문서): [업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다](<2026.11.17 업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다.md>)(배포 단위 유지 결정을 대체), [접근 정책은 SecurityPolicy 선언으로 관리한다](<2026.06.04 접근 정책은 SecurityPolicy 선언으로 관리한다.md>), [IP 밴은 MySQL이 SSOT이고 Redis는 enforcement projection이다](<2026.08.09 IP 밴은 MySQL이 SSOT이고 Redis는 enforcement projection이다.md>), [API 문서는 springdoc 런타임 OpenAPI로 제공한다](<2026.08.03 API 문서는 springdoc 런타임 OpenAPI로 제공한다.md>)

## Context(배경)

product와 admin은 같은 업무 모듈과 DB를 쓰면서도 JVM, Hikari 풀, 배포를 따로 두었다. 두 API를 따로 배포할 필요는 낮았고, JVM과 커넥션 풀이 중복되는 비용이 컸다. 그래서 두 API를 한 배포 단위로 합치기로 했다.

합치더라도 다음 제약은 지켜야 했다.

- admin의 외부 URL(`/admin/api/**`), 요청·응답 계약, 인증 결과를 바꾸지 않는다. admin 프론트엔드와 운영 도구가 그대로 쓸 수 있어야 한다.
- 두 앱은 같은 JWT 시크릿을 쓴다. 일반 사용자 토큰이 admin API에 닿지 않게 막는 장치는 admin 보안 체인뿐이다.
- admin은 context-path(`/admin/api`)를 썼고 product에는 context-path가 없다. 경로 판정, 악성 경로 규칙, 접근 제어 규칙은 모두 context-path를 뺀 경로를 기준으로 짜여 있었다.
- admin에서는 OSIV가 사실상 켜져 있었고, product에서는 꺼져 있다.
- admin 앱은 기동할 때 루트 관리자 초기화와 큐레이션 스펙 동기화를 실행했다. product는 레플리카가 여러 개라서 기동 작업이 동시에 실행된다.
- 한 번에 전환하면 차이를 찾기 어렵다. 기존 admin 앱과 나란히 띄워 응답을 비교할 수 있어야 한다.

## Decision(결정)

admin API를 product 앱(`bottlenote-product-api`)으로 옮기고, product 하나를 배포 단위로 쓴다. 진행 순서는 다음과 같다.

1. admin 앱(`bottlenote-admin-api`)은 수정하지 않고 그대로 둔다.
2. product 앱에 admin API를 모두 추가한다.
3. product와 admin을 함께 띄우고 섀도우 테스트로 API 호환성을 검증한다.
4. 검증과 배포가 끝나면 admin 앱을 제거한다.

새 부트 모듈이나 역할별 Deployment는 만들지 않는다. 모든 Pod가 같은 이미지로 `/api/**`와 `/admin/api/**`를 함께 처리한다.

이 결정이 바꾸는 것은 배포 단위뿐이다. 업무 경계를 Gradle 모듈로 분리한 [업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다](<2026.11.17 업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다.md>)의 모듈 구성, 위치, 의존 방향은 그대로 유지한다. 그 문서는 배포 단위 유지 결정 때문에 대체됨으로 표시되지만, 모듈 분리 결정은 계속 유효하다.

### 경로와 보안 체인

- admin 컨트롤러는 Kotlin 코드 그대로 product로 옮긴다. 기존 context-path는 `PathMatchConfigurer`의 prefix로 바꾼다. `/v1`을 쓰던 컨트롤러에는 `/admin/api/v1`을, v2 컨트롤러 두 개에는 `/admin/api`를 붙여 외부 URL을 유지한다.
- admin 컨트롤러를 판정하는 기준은 `AdminApi`의 패키지 목록 하나다. prefix, 보안 체인, 문서 분리, 예외 처리 범위가 모두 이 기준을 쓴다. 이 패키지에 product 컨트롤러가 들어오면 자동으로 admin에 편입되므로, ArchUnit 규칙이 이 패키지의 컨트롤러 이름을 admin 규칙(`Admin` 접두사, admin `AuthController`)으로 제한한다.
- `/admin/api/**` 요청은 product 체인보다 먼저 평가되는 admin 전용 `SecurityFilterChain`이 처리한다. 경로는 MVC와 같은 세그먼트 디코딩 기준으로 판정하고, ERROR dispatch에서는 원래 요청 URI로 체인을 고른다. 필터 구성, 인가 규칙, CORS는 기존 admin 앱과 같게 둔다. product 체인에는 admin 경로를 거부하는 규칙을 두어, 체인 선택이 어긋나더라도 admin API가 열리지 않게 한다.
- 악성 경로 규칙은 admin 앱과 마찬가지로 mount(`/admin/api`)를 뺀 안쪽 경로로 판정한다.

### 접근 제어

- admin 경로는 기존 admin 앱 설정을 옮긴 `bottlenote.admin-access-control`(네임스페이스 `admin`, 기본 300/60, unknown-IP 20/60, `/v1/auth` 30/60, 관리 평면 `/v1/access-control`)으로 만든 별도 `AccessControlService`와 `AccessControlFilter`가 평가한다. product 설정과 동작은 바꾸지 않는다.
- 평가에 쓰는 경로는 MVC와 같은 세그먼트 해석으로 mount를 뺀 경로다. 그래서 mount를 인코딩한 요청(`/admin/%61pi/...`)도 정상 경로와 같은 한도, 같은 버킷, 같은 관리 평면 예외를 받는다. URL 전체를 반복해서 디코딩하지 않는다.
- Redis 저장소, ban 목록, ban snapshot, 지표는 product와 공유한다. ban 키는 원래 두 앱이 공유했고, rate-limit 키는 네임스페이스로 나뉜다. 켜고 끄는 기준은 저장소를 만드는 `bottlenote.access-control.enabled` 하나다.
- access-control 모듈은 고치지 않는다.

### OSIV

- `spring.jpa.open-in-view`는 product와 같이 끈다. `/admin/api/**`에만 `OpenEntityManagerInViewInterceptor`를 등록해, admin 핸들러가 기대하던 지연 로딩 동작을 유지한다.

### 기동 작업

- 루트 관리자 초기화(`AuthController.onApplicationReady`, `RootAdminProperties`, `ROOT_ADMIN_*` 설정)는 더는 필요하지 않다는 결정에 따라 product로 옮기지 않고 폐기한다.
- 큐레이션 스펙 동기화(`CurationSpecResourceSyncRunner`)는 product의 모든 레플리카가 기동할 때 실행한다. 여러 레플리카가 같은 code를 동시에 insert해 유니크 제약 위반이나 잠금 충돌이 나면 최대 3회까지 다시 시도한다. 다시 실행하면 먼저 커밋된 행을 찾아 update 경로로 수렴한다. 스펙 검증 실패처럼 결정적인 오류는 재시도하지 않고 기존처럼 기동을 실패시킨다. `curation.spec-sync.enabled`로 끌 수 있다.

### 문서

- product 문서(`/api/v1/openapi.product.json`)는 admin 경로를 빼고 기존 내용을 유지한다.
- admin 문서(`/admin/api/v1/openapi.admin.json`, `.yaml`)는 별도 `OpenApiWebMvcResource`로 만든다. admin 전용 customizer와 springdoc 기본 customizer만 써서 기존 admin 문서와 같은 내용을 낸다. JSON 문서는 공개하고 YAML 문서는 인증을 요구하며, 이것도 admin 앱과 같다.

### 그 밖의 설정

- admin CORS(`app.cors.admin.*`), multipart 한도(5MB/6MB), 방문자 통계 제외 규칙은 기존 admin 앱 값을 product 설정으로 옮긴다. multipart 한도는 전역 설정이다.
- Tomcat, Hikari, JDBC `socketTimeout`은 product 값을 admin 경로에도 적용한다.

### Rejected Alternatives(선택하지 않은 대안)

- 새 부트 모듈(`bottlenote-api`)과 새 배포 단위: 기존 product 배포 파이프라인과 이미지를 그대로 쓸 수 있으므로 만들지 않는다.
- 같은 이미지를 product용과 admin용 Deployment로 나누는 방식: JVM과 커넥션 풀의 중복을 줄이려는 목적과 맞지 않아 쓰지 않는다.
- admin 경로 규칙을 product의 access-control 설정에 합치는 방식: unknown-IP 한도와 버킷이 product와 섞인다. 또 이 설정은 raw URI의 문자열 prefix로 규칙을 고르므로, mount를 인코딩한 요청이 admin 규칙과 관리 평면 예외를 벗어난다.
- admin 앱처럼 OSIV를 전역으로 켜는 방식: product 경로에서 커넥션을 점유하는 시간이 늘어난다.

## Status(상태)

Accepted(승인됨)

- Implementation Record(적용 기록): 2026.11.19에 2단계(product에 admin API 추가)를 작업 트리에 미커밋 상태로 적용했다. 3단계 섀도우 검증은 진행 중이며, 4단계(admin 앱 제거)는 적용하지 않았다.
- Implementation Record(적용 기록): 2026.11.20에 4단계 중 저장소와 개발 환경 부분을 작업 트리에 미커밋 상태로 적용했다.
  - `bottlenote-admin-api` 모듈과 `Dockerfile-admin`을 제거했다. admin 테스트는 product 모듈로 옮겼다. 이식한 통합 테스트는 `admin_integration` 태그와 product 모듈의 `admin_integration_test` 태스크(`testcontainers.db.name=bottlenote_admin`)를 그대로 쓰고, CI는 product의 `integration_test`와 `admin_integration_test`를 병렬로 실행한다.
  - 테스트 이식 결과: admin 통합 테스트 498개를 모두 옮겼고, product `admin_integration_test`에서 497개가 통과하고 1개(환경 변수로 켜는 성능 측정 테스트)는 원래처럼 건너뛴다. admin `test` 태스크의 54개 중 단위 테스트 46개를 옮겨 product `unit_test`에서 통과했다. 나머지 8개는 product 규칙 테스트와 조건이 같은 중복 규칙 테스트(`ControllerLayerRules`, `ModuleBoundaryRules`)라 옮기지 않았다. 옮긴 테스트는 admin 앱 기준 경로(`/v1/...`)로 요청하고, 테스트 설정(`AdminApiMountTestConfig`)이 `/admin/api`를 붙인다.
  - 개발 환경은 `deploy_development_applications.yml`이 product 모듈 jar를 새 이미지 `bottlenote-api`(`api_<short sha>`, 채널 태그 `api_latest_development`)로 발행하고, 개발 클러스터의 새 `api` Deployment·Service에만 배포한다. 새 부트 모듈이 아니라 기존 product 모듈의 jar와 `Dockerfile`을 쓴다. 개발 `product-api`·`admin-api`는 이미지를 더 발행하지 않으므로 FE 연동 뒤 교체할 때까지 마지막 이미지로 고정된다.
  - 운영은 전환하지 않았다. 운영 workflow(`release_pr_create`, `release_pr_merged`, `hotfix_pr_merged`, `deploy_release_applications`), 운영 overlay, 운영 Image Updater는 그대로이며 운영 배포 단위는 아직 product와 admin 둘이다. 제거 이후의 main 소스로는 운영 `admin`·`both` 릴리즈를 실행할 수 없고, `product` 릴리즈는 admin API가 포함된 이미지를 운영 product에 배포한다. 과거 `deployed` 태그에서 잘린 핫픽스는 그 소스의 admin 모듈로 기존처럼 빌드된다. 상세 제약은 `릴리즈 지침.md`에 적었다.

## Consequences(결과와 영향)

- 운영 Pod 수와 스펙은 workspace#564에서 정한다(product 2개와 admin 1개를 api 2개로 줄인다). admin API와 product API가 같은 JVM, 커넥션 풀, Tomcat 스레드를 쓰므로 한쪽 부하가 다른 쪽 응답에 영향을 줄 수 있다.
- admin 앱의 actuator(`/admin/api/actuator/**`), 정적 페이지(`/admin/api/`, `index.html`, `favicon.ico`), `/admin/api/error`는 제공하지 않는다. admin 프로브와 모니터링 경로는 `/actuator/**`로 바꿔야 한다.
- admin 경로에도 product의 JDBC `socketTimeout`(dev·prod 8초)이 적용된다. 8초를 넘는 admin 조회나 일괄 작업은 실패할 수 있다.
- product 경로에도 multipart 한도 5MB/6MB가 적용된다. product에는 multipart 엔드포인트가 없다.
- admin 패키지에 새 컨트롤러를 둘 때는 `Admin` 접두사 규칙을 따라야 한다. 규칙을 어기면 ArchUnit 검사가 실패한다.
- 운영 환경 변수로 admin 앱의 `bottlenote.access-control.*`를 덮어쓰고 있었다면, 같은 값을 `bottlenote.admin-access-control.*`로 옮겨야 한다.
- 전환 기간에 admin-old와 product-new가 함께 운영되는 동안에는 두 앱이 기동할 때마다 큐레이션 스펙 동기화를 함께 실행한다. admin-old의 동기화에는 재시도가 없다. 그래서 새 스펙 code가 추가된 배포에서 두 앱이 같은 code를 동시에 insert하면 유니크 제약 충돌로 admin-old 기동이 실패할 수 있다. product-new는 재시도해 update 경로로 수렴한다.
- product `SecurityConfig`는 원래 `SecurityContextHolder` 전략을 `MODE_INHERITABLETHREADLOCAL`로 바꿨다. 이 전략에서는 스레드 풀 워커가 만들어질 때의 인증을 계속 들고 있다가, 재사용될 때 다른 작업의 JPA 감사 컬럼에 그 인증을 남길 수 있다. admin 요청이 같은 앱에서 돌면 관리자 인증도 섞일 수 있으므로 기본 전략(`MODE_THREADLOCAL`)으로 되돌렸다. 대신 `@Async` 작업에는 `TaskDecorator`가 제출 시점의 인증만 전달하고, 실행이 끝나면 워커에서 지운다. 이 동작은 `AsyncSecurityContextIntegrationTest`와 `ProductionConfigContextStartupIntegrationTest`가 고정한다.
- 2단계와 3단계 동안에는 같은 admin 코드가 admin 앱과 product 앱에 함께 있어서 양쪽을 함께 고쳐야 했다. 2026.11.20에 admin 모듈을 제거하고 admin 테스트를 product로 옮겼으므로, 지금은 admin 코드와 테스트가 product 모듈에만 있다.
- admin 앱 제거에 맞춰 `CLAUDE.md`·`AGENTS.md`의 모듈 구조 설명을 갱신했다. [업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다](<2026.11.17 업무 경계를 Gradle 모듈로 분리하고 기존 배포 단위는 유지한다.md>)의 본문은 당시 결정의 기록으로 두고, 배포 단위 결정이 대체된 사실은 그 문서의 Status와 개정 이력에 적었다.
- 섀도우 검증 결과와 남은 차이는 workspace#564와 PR 본문에 남긴다.
