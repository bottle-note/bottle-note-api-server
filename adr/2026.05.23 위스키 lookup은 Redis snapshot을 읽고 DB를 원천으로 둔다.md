# ADR: 위스키 lookup은 Redis snapshot을 읽고 DB를 원천으로 둔다

- 상태: 적용됨
- 결정일: 2026.05.23 (Admin 분리 2026.08.16, 완전 실패 503 노출 2026.08.23)
- 대상: `bottlenote-mono` alcohols 도메인, `bottlenote-product-api`, `bottlenote-admin-api`
- 원본 계획: `plan/complete/alcohol-lookup.md` (git 히스토리)

## 결정

- FE의 위스키 선택 컴포넌트용 고속 조회 `GET /api/v1/alcohols/lookup`을 일반 검색과 분리해 추가한다. 응답은 핵심 필드(`alcoholId`, 이름, 카테고리, 지역, 증류소, `imageUrl`)만 담고 별점·좋아요·리뷰 수·pick 여부 같은 집계·개인화 필드는 제외한다.
- DB가 원천이고 Redis는 읽기 전용 lookup snapshot(`alcohol:lookup:snapshot:v1`)이다. Product API가 5분 주기로 snapshot을 동기화하고, 요청 시 snapshot을 메모리 stream으로 필터링해 cursor 페이지를 만든다. Redis miss 시 DB fallback, DB source가 0건이면 snapshot을 덮어쓰지 않는다.
- 공개 API에서 `source=DATABASE` 선택은 제거한다. k6 비교(DB p95 2128ms vs Redis p95 163ms)로 Redis 경로가 확정된 뒤 검증용 경로를 지웠다.
- 각 pod는 Redis snapshot version으로 무효화되는 파싱된 로컬 캐시를 둘 수 있다(`ALCOHOL_LOOKUP_LOCAL_CACHE_ENABLED`). Redis token 역색인과 category/region pre-bucket 파일럿은 p95 개선이 없어 롤백하고 코드도 제거했다.
- RediSearch, Redis Stack, OpenSearch, Meilisearch 등 추가 인프라는 도입하지 않는다.
- Admin lookup은 Product `AlcoholLookupService`를 직접 쓰지 않고 `AdminAlcoholLookupService`로 분리하며 snapshot 조회만 `AlcoholLookupSnapshotService`로 공유한다(#404).

## 배경

기존 `/api/v1/alcohols/search`는 일반 검색 화면까지 담당하는 무거운 경로였고, 리뷰 작성·어드민 선택 컴포넌트는 300ms debounce로 짧은 키워드를 반복 호출했다. 대상 데이터는 최대 2만 건 수준으로 전체를 메모리에 올려도 되는 규모였다.

## 선택하지 않은 대안

- DB 직접 조회 유지: 동일 부하에서 p95가 13배 느렸다.
- Redis 토큰 역색인 / pre-bucket: 로컬 측정에서 p95 개선 없음, p99는 타임아웃 꼬리에 지배됨. 롤백.
- 검색 엔진 도입: 이 단계의 목표 대비 운영 컴포넌트가 과도하다.

## 결과와 비용

- snapshot 동기화 지연(최대 5분)을 허용한다. 신규 등록 주류는 즉시 lookup에 나타나지 않는다.
- 다중 pod의 로컬 캐시는 version key로 staleness를 감지하지만 stale-read 창이 존재한다.
- Redis와 DB가 모두 실패하면 503으로 노출한다(2026.08.23).
